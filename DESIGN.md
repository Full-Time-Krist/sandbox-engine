# Концепция проекта: 3D-воксельная песочница

> Рабочий документ. Итог первого обсуждения идеи (2026-10-12).
> Обновлён 2026-10-12: этапы 0 и 1 завершены. Правила, действующие в коде, — раздел 8, этап 1 — раздел 9, план этапа 2 — раздел 10.
> Рабочее название проекта пока не выбрано (временно `Sandbox`).

## 1. Идея

**Абсолютная песочница**, перенасыщенная механиками. Игра не ведёт игрока за руку, он сам решает, что и как использовать.

- **Жанр:** «всё». Любой стиль игры, который можно представить, должен быть реализуем.
- **Вдохновение:** Minecraft, Terraria, Stardew Valley, Animal Crossing, Hytale и моды к ним.
- **Платформа:** ПК.
- **Графика:** 3D (воксели).
- **Масштаб:** долгоживущий проект с возможностью бесконечного развития.
- **Команда:** пока один разработчик, позже к проекту подключатся энтузиасты.
- **Мультиплеер:** пока не нужен, но архитектура закладывается под него с самого начала.

## 2. Ключевой принцип

Бесконечная песочница получается не из сотни механик на старте, а из **расширяемой архитектуры**.

Цель формулируется так:
> Движок и архитектура, в которых добавить любую новую механику дёшево,
> плюс небольшое, но цепляющее ядро геймплея, вокруг которого всё растёт.

Так развивались и игры-ориентиры: у Minecraft было «ставь и ломай блоки», у Terraria «копай, строй, сражайся». Механики наросли потом.

## 3. Почему свой движок

- Не упираемся в чужие ограничения. Но у Terraria проблема в её собственном старом коде, а не в стороннем движке, так что **решает архитектура**.
- «Самописный» **не значит писать всё с нуля**. Низкий уровень (окна, ввод, графический API, звук) берём готовыми библиотеками.
- Своими будут архитектура, мир, игровые системы и моддинг, то есть всё, что определяет ограничения.

## 4. Архитектурные решения

1. **ECS (Entity Component System).** Блоки, предметы, мобы и игрок собираются из компонентов (`Edible`, `Flammable`, `Tool { MiningSpeed }`, `Growable`...). Новая механика — это новый компонент плюс система, без переписывания старого кода. Ориентир: система компонентов из новых версий Minecraft.
2. **Data-driven.** Контент описывается данными (JSON), а не кодом. Новый предмет — это файл, без перекомпиляции.
3. **«Ванилла — это тоже мод».** Весь базовый контент грузится через тот же API, что и пользовательские моды (как в Factorio). Возможности моддинга ничем не ограничены.
4. **Моды:** C#-сборки (DLL) + JSON-контент. Эту модель уже знает целевое сообщество (tModLoader, SMAPI, Vintage Story).
5. **Клиент и сервер внутри одного процесса** (как одиночная игра в современном Minecraft). Это «заглушка» под мультиплеер:
   - клиент только рисует и отправляет действия игрока;
   - вся логика мира живёт на сервере;
   - пока они общаются сообщениями в памяти; для мультиплеера меняется только транспорт.
6. **Рендер за абстракцией**, чтобы позже сменить графический API без переписывания игры.

## 5. Технологический стек

**Язык: C# (.NET 10).**

Почему C#:
- Есть живое доказательство: **Vintage Story**, 3D-воксельная песочница на самописном C#-движке от маленькой команды, с одним из лучших API для модов в жанре.
- Моддинг почти бесплатный (загрузка сборок), сообщество энтузиастов знает C#.
- Высокая скорость разработки, что критично для одного человека.
- Производительности хватит: горячие места (построение мешей) оптимизируются через `Span`, SIMD и многопоточность. В игровом цикле избегаем аллокаций, чтобы не было пауз сборщика мусора.
- У разработчика уже есть опыт: курсовой проект на C# и несколько игр на Unity.

Альтернативы, которые рассмотрели:
- **Rust:** надёжность и производительность, но крутая кривая обучения, медленнее для экспериментов, моддинг сложнее.
- **C++:** максимум контроля, но в одиночку тяжело, а моды на нативном коде хрупкие.

| Задача | Решение |
|---|---|
| Окно, ввод, графика | Silk.NET |
| Рендер | OpenGL 4.6 на старте (за абстракцией, позже возможен Vulkan) |
| Текстуры блоков | массив текстур (`GL_TEXTURE_2D_ARRAY`), один слой на текстуру |
| Загрузка изображений | StbImageSharp |
| ECS | Arch (готовая библиотека) или своя реализация |
| Контент | JSON + реестр компонентов |
| Физика | своя AABB-коллизия с вокселями |
| Звук | OpenAL (через Silk.NET) |
| Тесты | xUnit |
| Шум для генерации мира | FastNoiseLite (MIT, один файл в репозитории) |
| Сохранения | SQLite (Microsoft.Data.Sqlite) |
| Сжатие чанков | палитра + Deflate (System.IO.Compression) |

## 6. Структура решения

| Проект | Назначение | Зависит от |
|---|---|---|
| `src/Engine` | низкий уровень: окно, рендер, ввод, звук, утилиты. Ничего не знает об игре | — |
| `src/Shared` | общие типы, мир и блоки, протокол сообщений клиент ↔ сервер | — |
| `src/Server` | логика мира, тики, генерация, сохранения | Shared |
| `src/Client` | отрисовка, интерфейс, ввод игрока; запускаемый проект | Engine, Shared, Server |

Server не зависит от Engine: сервер должен уметь работать без окна и видеокарты (выделенный сервер).

## 8. Как устроено и почему: действующие правила

Правила, которые уже действуют в коде. Новый код должен им следовать.

**Сборка**
- Название игры задаётся одной строкой: `GameName` в `Directory.Build.props`. Из него получаются имена сборок и exe. Namespace'ы нейтральные (`Engine`, `Client`...), в коде название игры не пишем.
- Версии NuGet-пакетов хранятся только в `Directory.Packages.props`, в csproj пишется лишь имя пакета.
- Ассеты (шейдеры, текстуры) лежат в `src/Client/Assets` и при сборке копируются рядом с exe.
- Тесты запускаются командой `dotnet test --solution Game.slnx`. xUnit v3 работает через Microsoft.Testing.Platform, он включён в `global.json`: без этого `dotnet test` в .NET 10 падает с ошибкой.

**Рендер**
- OpenGL 4.6 core, все объекты через DSA (`glCreate*`, `glNamed*`), без `glBind*` для настройки.
- Обёртки в `Engine.Graphics`: `GpuBuffer<T>`, `VertexArrayObject`, `ShaderProgram`. Имена не совпадают с типами Silk.NET (`Shader`, `VertexArray`), чтобы не было конфликтов.
- В Debug-сборке драйвер сам пишет ошибки OpenGL в консоль (`GlDebug`), синхронно, со стеком вызова.
- Глубина NDC от 0 до 1 (`glClipControl`): матрицы `System.Numerics` используются как есть, позже можно включить reversed-Z.
- Лицевые грани — с обходом против часовой стрелки, если смотреть снаружи; задние отсекаются.
- Матрицы `System.Numerics` передаются в шейдер без транспонирования. Порядок в C#: `M * V * P`, в GLSL: `P * V * M * v`.
- Текстуры блоков (этап 1): массив текстур, файлы `src/Client/Assets/Textures/Blocks/{имя}.png`. Заглушки генерирует `tools/generate_textures.py`; свою текстуру можно подложить вместо заглушки, сохранив имя файла. Строки картинки не переворачиваются: v = 0 — верх картинки, на боковых гранях он у верха блока. Слой 0 всегда «нет текстуры» (розово-чёрная шахматка): им рисуются блоки без описания и текстуры без файла.
- Внешний вид блоков (какая текстура на какой грани) описывает клиент (`BlockVisuals`), а не реестр в Shared: серверу он не нужен.
- Индексированная отрисовка — только через `glDrawRangeElements` с явным диапазоном индексов (`VertexArrayObject.DrawIndexed`). С обычным `glDrawElements` драйвер Intel при каждом вызове просматривает буфер индексов на CPU: на 128 чанках это было 23 мс за кадр вместо 0,5 мс (найдено на шаге 1.5).
- Производительность меряем, а не угадываем: сначала разделить кадр на части (CPU, GPU через `glFinish`), потом искать причину.

**Клиент и мир**
- Числовые id блоков у клиента и сервера должны совпадать. Сервер присылает таблицу имён в `JoinAccepted`, клиент сверяет её со своим реестром и при расхождении останавливается с ошибкой.
- Чанки передаются сообщением `ChunkData` в сжатом виде (`ChunkCodec`: палитра + индексы разрядности 0/1/2/4/8/16 бит + Deflate, первый байт — версия формата). Этот же формат пойдёт в сохранения. Пустой чанк занимает 8 байт, поэтому отдельного случая для него нет.
- Данные из сети и с диска не считаются надёжными: `ChunkCodec.Decode` проверяет версию, размеры, каждый индекс и ограничивает объём распаковки, а при ошибке бросает `InvalidDataException`.
- Когда клиент получает чанк, перестраиваются меши его и загруженных соседей по граням: у соседей меняются граничные грани. Когда меняется блок на границе чанка, перестраивается и сосед за этой границей.

**Предметы и действия игрока**
- Кнопки мыши означают не «сломать/поставить», а действия предмета в руке: основное (ЛКМ) и дополнительное (ПКМ). Клиент шлёт `UseItem(действие, точка взгляда, направление)`, а что произойдёт, решает сервер по предмету: `IItemBehavior`. Сейчас у всех предметов поведение блока (ЛКМ ломает, ПКМ ставит). Новый вид предмета (инструмент, еда, оружие) — новая реализация `IItemBehavior`, без новых сообщений и без правок клиента.
- Сервер не верит клиенту на слово: повторяет луч по своей копии мира и проверяет, что точка взгляда рядом с известной ему позицией игрока.
- Блоки на сервере меняются только через одну точку (`IBlockEditor`), которая сразу рассылает `BlockChanged` всем игрокам.
- Хотбар (6 слотов) авторитетно хранится на сервере; клиент шлёт только выбор слота. Пока слоты содержат блоки, позже — стопки предметов.

**Игровой цикл**
- Логика идёт фиксированными тиками: 20 TPS (`Shared.GameTime`), независимо от FPS. Длинные кадры (больше 0,25 с) обрезаются, чтобы игра не пыталась догнать время сотнями тиков подряд.
- Рендер интерполирует между двумя последними состояниями: `Lerp(previous, current, alpha)`. Плата за плавность — отставание на один тик (50 мс).

**Ввод**
- Нажатия (`WasKeyPressed`) и движение мыши относятся к кадру. В тике их читать нельзя: при FPS выше TPS большинство кадров проходит без тиков, и нажатие потеряется. В тике читается только удержание (`IsKeyDown`).
- Взгляд мышью применяется каждый кадр (мгновенный отклик), движение — в тиках.

**Клиент и сервер**
- Клиент и сервер общаются только сообщениями через `IConnection`. Для одиночной игры — `LocalConnection` (две потокобезопасные очереди), для мультиплеера будет сетевая реализация.
- Сообщения — неизменяемые `record`: в памяти они передаются по ссылке.
- Встроенный сервер работает в своём потоке (`ServerHost`) с фиксированным тиком 20 TPS и не зависит от кадров клиента: пока окно тащат мышью, мир живёт. Время тиков отсчитывается от старта, поэтому средняя частота точная; отдельный промежуток между тиками может доходить до ~62 мс из-за точности таймера Windows (15,6 мс). Отставание больше 0,25 с не догоняется.
- Всё состояние `GameServer` принадлежит потоку сервера и меняется только внутри `Tick`. Снаружи можно лишь подключать клиентов (`Connect` кладёт соединение в потокобезопасную очередь, сессия появляется в следующем тике) и обмениваться сообщениями. Новый вход в сервер из чужого потока — только через такую же очередь.
- Если поток сервера упал, исключение сохраняется в `ServerHost.Fault`, а клиент в следующем тике останавливается с этой ошибкой, а не рисует замерший мир.
- Кадры клиента дольше 0,25 с пишутся в лог (`[Engine] Кадр длился …`).
- Сервер принимает только сообщения, разрешённые в текущем состоянии сессии; незнакомое пишется в лог, а не роняет сервер.

**Прочее**
- Консоль выводит UTF-8, чтобы кириллица не ломалась в перенаправленных логах.

## 9. План этапа 1: воксели

**Цель:** летаем над текстурированным ландшафтом примерно 256×256 блоков, ломаем и ставим блоки. FPS не ниже 60 на встроенной видеокарте (Intel UHD 730), автотесты зелёные.

### Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Размер чанка | 32×32×32, кубические чанки | Мир не ограничен по высоте. Чанков в 8 раз меньше, чем при 16³, значит меньше вызовов отрисовки (важно для встроенной видеокарты). Плата: перестроение меша после изменения блока дороже, около 1–3 мс |
| Хранение блоков | плоский массив `ushort[32768]`, индекс `x + z·32 + y·32·32` | Просто и быстро. Сжатие палитрой — позже, когда понадобится память или сеть |
| Идентификатор блока | числовой `BlockId` (`ushort`) в рантайме, строковый `"base:stone"` как постоянное имя | Числовые id раздаются при запуске, поэтому моды не конфликтуют за номера. В сохранениях и сети будет строковое имя или таблица соответствия. Воздух всегда 0 |
| Координаты | блок — `int`; чанк = `coord >> 5`, позиция внутри чанка = `coord & 31` | Деление `/ 32` для отрицательных координат даёт неверный чанк (−1 / 32 = 0, а нужен −1). Классический источник багов, его покрывают тесты |
| Позиции вершин | вершины в локальных координатах чанка, смещение чанка — через матрицу модели | Числа в меше маленькие и точные. Рендер относительно камеры (против дрожания вдали от центра мира) — на этапе 2 |
| Текстуры | массив текстур, 16×16, фильтрация nearest + mip-карты | Нет протекания соседних текстур, позже позволяет greedy meshing. Для начала — сгенерированные заглушки, их можно заменить файлами с теми же именами |
| Освещение | постоянная яркость по направлению грани: верх 1.0, север/юг 0.8, восток/запад 0.6, низ 0.5 | Объём без системы освещения. Настоящий свет и затенение углов (AO) — позже |
| Изменение блоков | только через сервер: клиент шлёт запрос, сервер проверяет и рассылает результат | Сервер — единственный владелец мира. Предсказания на клиенте пока нет: в одиночной игре задержка один тик (50 мс), её не видно |
| Построение мешей | в основном потоке, с замером времени | Сначала правильность, потом скорость. Замер станет точкой отсчёта для фонового построения на этапе 2 |

### Шаги

Каждый шаг заканчивается рабочей сборкой, проверкой и отдельным коммитом.

| # | Шаг | Что делаем | Как проверяем |
|---|---|---|---|
| 1.1 | Тесты и координаты | Проект `tests/Shared.Tests` (xUnit). Типы `BlockPos`, `ChunkPos` и перевод между мировыми, чанковыми и локальными координатами | Тесты, в том числе на отрицательные координаты и границы чанков |
| 1.2 | Блоки и чанк | `BlockId`, `BlockRegistry` (пока блоки регистрируются в коде: воздух, камень, земля, трава, песок, бревно, доски), класс `Chunk` с массивом блоков | Тесты: чтение и запись блоков, границы массива, воздух по умолчанию |
| 1.3 | Меш чанка | Построение меша с отсечением скрытых граней (грань строится, только если сосед — воздух). Пока цвет вместо текстур, яркость по направлению грани. Тестовый чанк создаётся на клиенте | Тесты: один блок — 6 граней, два соседних — 10, сплошной чанк — только внешние грани. Скриншот |
| 1.4 | Массив текстур | `TextureArray` в Engine (DSA, mip-карты), загрузка PNG через StbImageSharp, заглушки 16×16. У каждого блока свои текстуры на верх, бока и низ | Скриншот: трава сверху зелёная, сбоку с земляной полосой. Нет ошибок GL |
| 1.5 | Мир на сервере | `World` из чанков на сервере, мир фиксированного размера 8×3×8 чанков (256×96×256 блоков), холмы по простой формуле (шум — на этапе 2). Сообщение `ChunkData` с копией блоков. Клиент хранит свои копии чанков и строит меши с учётом соседних чанков на границах. Отладочные кубы удаляем | Скриншот ландшафта, на стыках чанков нет лишних граней. Время построения мешей в логе, FPS в заголовке |
| 1.6 | Прицел и выделение | Поиск блока под прицелом алгоритмом DDA (Amanatides–Woo) в Shared: он нужен и серверу для проверки. Дальность 6 блоков. Каркасная рамка вокруг выбранного блока и перекрестие в центре экрана | Тесты DDA: прямо, по диагонали, через границу чанка, промах. Скриншот рамки |
| 1.7 | Ломание и установка | ЛКМ ломает, ПКМ ставит, клавиши 1–6 выбирают блок. Сделано через действия предмета (`UseItem` + `IItemBehavior`), чтобы позже ЛКМ и ПКМ зависели от предмета в руке. Сообщения `BreakBlock` / `PlaceBlock` → проверка на сервере (чанк есть, дальность, цель не воздух / место свободно) → `BlockChanged` всем клиентам → клиент перестраивает меш чанка, а если блок на границе — и соседнего | Скриптом ломаем и ставим блоки, сравниваем скриншоты. Блок на границе чанка не оставляет дыр |

### Не входит в этап 1

Бесконечный мир и шум, многопоточность, сохранения, greedy meshing, затенение углов и освещение, отсечение невидимых чанков, коллизии и гравитация (летаем сквозь блоки), инвентарь, блоки из JSON. Всё это есть в дорожной карте на следующих этапах.

## 10. План этапа 2: бесконечный мир

**Цель:** летим в любую сторону сколько угодно. Мир подгружается вокруг игрока и выгружается позади без заметных подвисаний (ни один кадр не дольше 20 мс). Не меньше 60 FPS на Intel UHD 730 при дальности 6 чанков. Изменения мира сохраняются и переживают перезапуск.

### Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Где работает сервер | в своём потоке, с собственным циклом фиксированного тика. Клиент и сервер общаются только через очереди (они уже потокобезопасные) | Пока окно тащат мышью, мир продолжает жить. Тяжёлая работа сервера не отнимает время у кадров |
| Генерация чанков | в фоновых потоках сервера. Основной поток сервера только забирает готовые чанки | Генерация чанка — миллисекунды. Сотня чанков при входе подвесила бы тик сервера |
| Шум | FastNoiseLite, сид мира хранится в сохранении | Готовые OpenSimplex2, фракталы, искажение координат. Генерация детерминирована по сиду |
| Высота мира | без предела по Y (кубические чанки). Рельеф генерируется примерно в диапазоне от −64 до +192, ниже — камень, выше — воздух | Бесконечный по высоте мир без особых случаев в коде |
| Какие чанки загружать | сервер ведёт для каждого игрока набор чанков в радиусе: по горизонтали — дальность прорисовки, по вертикали — меньше (около ±4). Недостающие встают в очередь от ближних к дальним; ушедшие за радиус с запасом выгружаются у клиента (`ChunkUnload`) | Запас при выгрузке (гистерезис) нужен, чтобы чанки на границе не загружались и выгружались туда-сюда, когда игрок топчется на месте |
| Дальность прорисовки | 6 чанков (192 блока) по умолчанию, позже — настройка | Рассчитано на встроенную видеокарту. Это как 12 чанков в Minecraft |
| Скорость отправки | не больше N чанков клиенту за тик | Иначе при входе клиент получит сотни чанков разом |
| Сжатие чанков | палитра (список разных блоков чанка + индексы наименьшей нужной разрядности) + Deflate. Один формат для сети и сохранений | Чанк 64 КБ превращается в единицы КБ. Нужно и для сети, и для диска |
| Построение мешей | в пуле фоновых потоков, по неизменяемому снимку чанка и его соседей. Основной поток только загружает готовые меши в видеопамять, не больше заданного числа за кадр | Мир клиента меняется только в основном потоке, поэтому фоновой задаче нужен снимок. Ограничение на кадр — чтобы сотни мешей не дали один длинный кадр |
| Отсечение невидимого | frustum culling: чанк рисуется, только если его куб пересекает пирамиду видимости камеры | Примерно половина чанков всегда позади камеры |
| Рендер относительно камеры | смещение чанка от камеры считается в `double`, в шейдер идёт уже маленькое число | Вдали от центра мира (сотни тысяч блоков) `float` теряет точность, и мир начинает дрожать |
| Формат сохранения | SQLite, один файл на мир: таблица `meta` (сид, версия формата, позиция игрока, таблица имён блоков) и таблица `chunks` (позиция → сжатый блок данных) | Атомарные записи: сбой не испортит мир. Так делает Vintage Story |
| Что сохранять | все сгенерированные чанки | Генератор будет меняться по ходу разработки. Если хранить только изменённые, нетронутые места пересоздадутся по-новому, и рядом с постройками появятся обрывы |
| Когда сохранять | при выгрузке чанка, автосохранение раз в минуту, при выходе | Потеря при сбое — не больше минуты игры |
| Id блоков в сохранении | в файле хранится таблица имён блоков; при загрузке числовые id переводятся по именам | Числовые id могут измениться при добавлении блоков и модов, имена — нет |
| Где лежат сохранения | `%LOCALAPPDATA%\<название игры>\Saves\` | Не в папке сборки: её удаляет `dotnet clean`. Название берётся из `GameName` |

### Шаги

Каждый шаг заканчивается рабочей сборкой, проверкой и отдельным коммитом.

| # | Шаг | Что делаем | Как проверяем |
|---|---|---|---|
| 2.1 | Сервер в своём потоке ✅ | `ServerHost`: поток с циклом фиксированного тика, корректный запуск и остановка при закрытии окна. Клиент больше не тикает сервер сам. Статистика тиков в логе раз в 10 с | Тесты запуска и остановки. Вживую: пока окно тащат мышью, сервер продолжает тикать (видно в логе) |
| 2.2 | Сжатие чанков ✅ | `ChunkCodec` в Shared: палитра + Deflate. `ChunkData` передаёт сжатые байты. Замер (Release): чанк с рельефом 1,25 КБ в среднем вместо 64 КБ, кодирование и распаковка ~0,13 мс; весь мир 8×3×8 — 130 КБ вместо 12 МБ. В Debug распаковка ~0,35 мс | Тесты: туда и обратно для пустого, однородного, пёстрого чанка и чанка со всеми видами блоков. Замер размера и скорости |
| 2.3 | Генерация шумом | FastNoiseLite, сид мира. Рельеф: равнины, холмы и горы через смешивание нескольких шумов, песок у «уровня моря» (воды пока нет). Генерация в фоновых потоках сервера | Тесты: одинаковый сид — одинаковый мир, разный — разный. Скриншоты. Замер времени на чанк |
| 2.4 | Подгрузка вокруг игрока | Набор чанков игрока на сервере, очередь от ближних к дальним, `ChunkUnload` с запасом, ограничение отправки за тик. Сервер выгружает чанки, рядом с которыми нет игроков. Клиент удаляет чанки и их меши | Тесты: какие чанки грузить и выгружать при перемещении. Вживую: полёт скриптом на 2000 блоков — впереди всегда есть мир, память не растёт без предела |
| 2.5 | Меши в фоне | Снимки чанков, пул потоков, ограничение загрузки мешей в видеопамять за кадр | Тесты снимка. Замер самого длинного кадра при входе и в полёте (цель — не больше 20 мс) |
| 2.6 | Отсечение и точность | Frustum culling. Смещения чанков относительно камеры в `double` | Тест пересечения куба с пирамидой видимости. Число нарисованных чанков в заголовке окна. Телепорт на миллион блоков от центра — мир не дрожит |
| 2.7 | Сохранение и загрузка | SQLite: сид, таблица имён блоков, позиция игрока, чанки. Автосохранение, сохранение при выходе, загрузка существующего мира при запуске | Тесты на временной базе: сохранить → загрузить → те же блоки; перевод id по именам. Вживую: поставить блок, перезапустить игру — блок на месте |

Если после шага 2.6 по замерам не хватит FPS, добавим шаг оптимизации: упаковка вершин в 8 байт и greedy meshing.

### Не входит в этап 2

Вода и другие жидкости, пещеры, полноценные биомы, деревья и постройки при генерации, освещение и затенение углов, уровни детализации для дальних чанков, физика игрока, настоящий сетевой транспорт, меню выбора мира. Всё это — следующие этапы.
