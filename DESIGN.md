## 1. Идея

**Абсолютная песочница**, перенасыщенная механиками. Игра не ведёт игрока за руку, он сам решает, что и как использовать.

- **Жанр:** «всё». Любой стиль игры, который можно представить, должен быть реализуем.
- **Вдохновение:** Minecraft, Terraria, Stardew Valley, Animal Crossing, Hytale и моды к ним.
- **Платформа:** ПК.
- **Графика:** 3D (воксели).
- **Масштаб:** долгоживущий проект с возможностью бесконечного развития.
- **Команда:** пока один разработчик, позже к проекту подключатся энтузиасты.
- **Мультиплеер:** пока не нужен, но архитектура закладывается под него с самого начала.

## 2. Ключевой принцип

Бесконечная песочница получается не из сотни механик на старте, а из **расширяемой архитектуры**.

Цель формулируется так:
> Движок и архитектура, в которых добавить любую новую механику дёшево,
> плюс небольшое, но цепляющее ядро геймплея, вокруг которого всё растёт.

Так развивались и игры-ориентиры: у Minecraft было «ставь и ломай блоки», у Terraria «копай, строй, сражайся». Механики наросли потом.

## 3. Почему свой движок

- Не упираемся в чужие ограничения. Но у Terraria проблема в её собственном старом коде, а не в стороннем движке, так что **решает архитектура**.
- «Самописный» **не значит писать всё с нуля**. Низкий уровень (окна, ввод, графический API, звук) берём готовыми библиотеками.
- Своими будут архитектура, мир, игровые системы и моддинг, то есть всё, что определяет ограничения.

## 4. Архитектурные решения

1. **ECS (Entity Component System).** Блоки, предметы, мобы и игрок собираются из компонентов (`Edible`, `Flammable`, `Tool { MiningSpeed }`, `Growable`...). Новая механика — это новый компонент плюс система, без переписывания старого кода. Ориентир: система компонентов из новых версий Minecraft.
2. **Data-driven.** Контент описывается данными (JSON), а не кодом. Новый предмет — это файл, без перекомпиляции.
3. **«Ванилла — это тоже мод».** Весь базовый контент грузится через тот же API, что и пользовательские моды (как в Factorio). Возможности моддинга ничем не ограничены.
4. **Моды:** C#-сборки (DLL) + JSON-контент. Эту модель уже знает целевое сообщество (tModLoader, SMAPI, Vintage Story).
5. **Клиент и сервер внутри одного процесса** (как одиночная игра в современном Minecraft). Это «заглушка» под мультиплеер:
   - клиент только рисует и отправляет действия игрока;
   - вся логика мира живёт на сервере;
   - пока они общаются сообщениями в памяти; для мультиплеера меняется только транспорт.
6. **Рендер за абстракцией**, чтобы позже сменить графический API без переписывания игры.

## 5. Технологический стек

**Язык: C# (.NET 10).**

Почему C#:
- Есть живое доказательство: **Vintage Story**, 3D-воксельная песочница на самописном C#-движке от маленькой команды, с одним из лучших API для модов в жанре.
- Моддинг почти бесплатный (загрузка сборок), сообщество энтузиастов знает C#.
- Высокая скорость разработки, что критично для одного человека.
- Производительности хватит: горячие места (построение мешей) оптимизируются через `Span`, SIMD и многопоточность. В игровом цикле избегаем аллокаций, чтобы не было пауз сборщика мусора.
- У разработчика уже есть опыт: курсовой проект на C# и несколько игр на Unity.

Альтернативы, которые рассмотрели:
- **Rust:** надёжность и производительность, но крутая кривая обучения, медленнее для экспериментов, моддинг сложнее.
- **C++:** максимум контроля, но в одиночку тяжело, а моды на нативном коде хрупкие.

| Задача | Решение |
|---|---|
| Окно, ввод, графика | Silk.NET |
| Рендер | OpenGL 4.6 на старте (за абстракцией, позже возможен Vulkan) |
| Текстуры блоков | массив текстур (`GL_TEXTURE_2D_ARRAY`), один слой на текстуру |
| Загрузка изображений | StbImageSharp |
| 2D-интерфейс | свой (`Engine.Ui`): холст и `SpriteBatch` поверх OpenGL |
| Шрифт | TTF, растеризация при запуске — StbTrueTypeSharp; шрифт Press Start 2P (OFL) |
| ECS | своя небольшая (sparse set), с этапа 7 — для сущностей |
| Контент | JSON + реестр компонентов |
| Физика | своя AABB-коллизия с вокселями |
| Звук | OpenAL (через Silk.NET) |
| Тесты | xUnit |
| Шум для генерации мира | FastNoiseLite (MIT, один файл в репозитории) |

## 8. Как устроено и почему: действующие правила

Правила, которые уже действуют в коде. Новый код должен им следовать.

**Сборка**
- Название игры задаётся одной строкой: `GameName` в `Directory.Build.props`. Из него получаются имена сборок и exe. Namespace'ы нейтральные (`Engine`, `Client`...), в коде название игры не пишем.
- Версии NuGet-пакетов хранятся только в `Directory.Packages.props`, в csproj пишется лишь имя пакета.
- Ассеты (шейдеры, текстуры, шрифт) лежат в `src/Client/Assets` и при сборке копируются рядом с exe. Исключение — шейдеры интерфейса: они встроены в сборку Engine, чтобы движок не зависел от ассетов игры.
- Тесты запускаются командой `dotnet test --solution Game.slnx`. xUnit v3 работает через Microsoft.Testing.Platform, он включён в `global.json`: без этого `dotnet test` в .NET 10 падает с ошибкой.

**Рендер**
- OpenGL 4.6 core, все объекты через DSA (`glCreate*`, `glNamed*`), без `glBind*` для настройки.
- Обёртки в `Engine.Graphics`: `GpuBuffer<T>`, `VertexArrayObject`, `ShaderProgram`, `TextureArray`, `Texture2D`. Имена не совпадают с типами Silk.NET (`Shader`, `VertexArray`), чтобы не было конфликтов.
- В Debug-сборке драйвер сам пишет ошибки OpenGL в консоль (`GlDebug`), синхронно, со стеком вызова.
- Область отрисовки (`glViewport`) выставляется при загрузке по текущему размеру кадра и затем при каждом `FramebufferResize`. Тайловые оконные менеджеры (niri, Hyprland) меняют размер окна ещё до `Load`, и событие изменения размера тогда не приходит: без начального `glViewport` кадр рисовался в угол 1280×720, а интерфейс считал настоящий размер (найдено при первом запуске под Linux).
- Глубина NDC от 0 до 1 (`glClipControl`): матрицы `System.Numerics` используются как есть, позже можно включить reversed-Z.
- Лицевые грани — с обходом против часовой стрелки, если смотреть снаружи; задние отсекаются.
- Матрицы `System.Numerics` передаются в шейдер без транспонирования. Порядок в C#: `M * V * P`, в GLSL: `P * V * M * v`.
- Рендер относительно камеры: у `Camera` нет позиции, она всегда в начале координат, и `ViewProjection` содержит только поворот и проекцию. Смещение каждого объекта от глаза (`начало чанка − позиция глаза`) считается в `double` и только потом становится `float`-матрицей модели. Так мир не дрожит и на миллионах блоков от центра.
- Отсечение невидимого: чанк рисуется, только если его куб пересекает пирамиду видимости (`Frustum`, плоскости из `ViewProjection`). Отсечение может оставить лишнее, но не выбрасывает видимое. Число нарисованных чанков — в заголовке окна.
- Текстуры блоков (этап 1): массив текстур, файлы `src/Client/Assets/Textures/Blocks/{имя}.png`. Заглушки генерирует `tools/generate_textures.py`; свою текстуру можно подложить вместо заглушки, сохранив имя файла. Строки картинки не переворачиваются: v = 0 — верх картинки, на боковых гранях он у верха блока. Слой 0 всегда «нет текстуры» (розово-чёрная шахматка): им рисуются блоки без описания и текстуры без файла.
- Внешний вид блоков (какая текстура на какой грани) задаётся полем `textures` в JSON блока, но в реестр блоков (`BlockDefinition`) не попадает: загрузчик отдаёт его отдельной таблицей `ContentRegistries.BlockTextures`, и пользуется ей только клиент (`BlockVisuals.AppearancesFrom`, файлы — `TextureFiles`). Серверу внешний вид не нужен.
- Индексированная отрисовка — только через `glDrawRangeElements` с явным диапазоном индексов (`VertexArrayObject.DrawIndexed`). С обычным `glDrawElements` драйвер Intel при каждом вызове просматривает буфер индексов на CPU: на 128 чанках это было 23 мс за кадр вместо 0,5 мс (найдено на шаге 1.5).
- Производительность меряем, а не угадываем: сначала разделить кадр на части (CPU, GPU через `glFinish`), потом искать причину.
- Меши чанков строятся в фоновых потоках (`MeshBuildQueue`) по снимку (`ChunkSnapshot`: копия блоков и света чанка 34³ с рамкой из всех 26 соседей — по граням, рёбрам и углам; нет соседа — воздух под полным небом). Мир клиента меняется только в основном потоке, поэтому фоновой задаче нужна своя копия. Мешер и `BlockVisuals` только читают данные, их можно звать из нескольких потоков.
- **Освещённые меши** (с шага 8.3). Вершина (`ChunkVertex`, 36 байт): позиция, UV, слой, `Shade` = постоянная яркость грани (`BlockFace.Brightness`) × затенение угла, небесный и блочный свет (0–15, дробные). Свет вершины — среднее четырёх блоков перед гранью у этого угла (прямо, два сбоку, по диагонали), только прозрачных; затенение — по трём, кроме переднего (`ChunkMesher.OcclusionShade`: 0,5 / 0,65 / 0,8 / 1). Два боковых непрозрачных — угол закрыт целиком, диагональ не учитывается ни в затенении, ни в свете: свет не протекает сквозь стык. Квадрат делится по диагонали с меньшим перепадом яркости (затенение × свет). Кривую яркости, тёплый оттенок блочного света и яркость неба (`u_SkyBrightness`, пока всегда 1) применяет шейдер: `max(кривая(небо × яркость неба), кривая(блочный) × тёплый)`, кривая — 0,8 за уровень, уровень 0 — 0,05 (не чёрный). Та же кривая — в `item.frag`: предмет на земле освещён светом блока, где лежит (`ItemEntityRenderer.LightOf`). Трещины света не читают.
- Меш чанка строится, когда у него есть все 26 соседей, какие могут прийти (`ClientWorld.IsSurrounded`): каждый пришедший сосед по ребру или углу перестраивал бы меш, а при входе они приходят через ~0,3·d с (d — расстояние в чанках). Сосед за областью загрузки не придёт — его не ждём: сервер сообщает область (`ChunkArea`, теперь в `Shared.Voxels`) в `JoinAccepted`, клиент держит её центр в чанке игрока (`ClientWorld.LoadArea`, `Center`). Запасной путь — чанк не менялся `ChunkRenderer.SettleTime` (1 с): так строится и меш, чей сосед почему-то не пришёл (центры клиента и сервера на тик разошлись). Пустой чанк в построение не отправляется вовсе (меша у него нет; старый удаляется).
- Основной поток только снимает снимки «грязных» чанков (ближние к камере первыми) и загружает готовые меши в видеопамять. На каждое — бюджет времени на кадр (`ChunkRenderer.SubmitBudgetMs`, `UploadBudgetMs`, по 2 мс). Что не уложилось, ждёт следующего кадра.
- Готовый меш принимается, только если он построен по последней отправке этого чанка (`MeshVersions`). Устаревшие результаты (чанк снова изменился или выгрузился) отбрасываются. Старый меш рисуется, пока не готов новый.
- В логе клиента раз в 10 с: самый долгий кадр и число кадров дольше 20 мс (первый кадр после запуска не считается). Цель этапа 2 — ни одного такого кадра.

**Клиент и мир**
- Числовые id блоков и предметов у клиента и сервера должны совпадать. Сервер присылает таблицы имён в `JoinAccepted`, клиент сверяет их со своими реестрами и при расхождении останавливается с ошибкой.
- Чанки передаются сообщением `ChunkData` в сжатом виде (`ChunkCodec`: палитра + индексы разрядности 0/1/2/4/8/16 бит + Deflate, первый байт — версия формата). Этот же формат используется в сохранениях. Пустой чанк занимает 8 байт, поэтому отдельного случая для него нет. С шага 8.2 `ChunkData` несёт и свет чанка (`LightCodec` — тот же формат, значения — упакованный свет блока; одинаково освещённый чанк — 8 байт); в сохранение свет не пишется. Общая часть обоих кодеков — `PaletteCodec`.
- Данные из сети и с диска не считаются надёжными: `ChunkCodec.Decode` и `LightCodec.Decode` проверяют версию, размеры, каждый индекс (свет — и что значение не больше байта) и ограничивают объём распаковки, а при ошибке бросают `InvalidDataException`.
- Когда клиент получает чанк, перестраиваются меши его и всех 26 загруженных соседей: у соседей по граням меняются граничные грани, а у всех — свет и затенение вершин у края (их рамка читает крайние блоки нового чанка). Когда меняется блок у края чанка, перестраиваются соседи, в чью рамку он попадает: блок у грани — сосед за ней, у ребра — ещё два, в углу — семь. Новый свет чанка (`ChunkLightChanged`) перестраивает его меш, только если свет изменился, и соседей — только за изменившимися краями (`ClientWorld.SetLight` сравнивает старый и новый).
- Меш непустого чанка строится, только когда у клиента есть все шесть его соседей по граням (`ClientWorld.CanMesh`), и после «успокоения» (см. «Рендер»). Иначе при подгрузке по одному чанку меш перестраивался бы много раз. Поэтому сервер грузит на кольцо больше дальности прорисовки: крайнее кольцо нужно только как соседи.
- При выгрузке чанка (`ChunkUnload`) клиент удаляет его и меш, а соседей не перестраивает: их грани в сторону выгруженного чанка смотрят от игрока.

**Подгрузка вокруг игрока**
- Для каждого игрока сервер ведёт `PlayerChunkView`: какие чанки нужны и какие уже отправлены. Область — цилиндр: круг по горизонтали и полоса по высоте (`ChunkArea`). Три радиуса: дальность прорисовки (6 по горизонтали, ±4 по высоте), загрузка — на кольцо больше, выгрузка у клиента — ещё на 2 кольца дальше (гистерезис).
- Каждый тик сервер для каждого игрока: выгружает у клиента ушедшие за радиус выгрузки чанки, отправляет готовые недостающие от ближних к дальним, но не больше `MaxChunksPerTick` (16), и ставит в генерацию отсутствующие.
- Одновременно генерируется не больше `World.MaxGenerating` (64) чанков. Длинную очередь не копим: пока игрок летит, важное меняется, и сервер каждый тик заново выбирает ближайшие недостающие.
- Раз в секунду сервер выгружает из памяти чанки, которые не входят в область выгрузки ни одного игрока. Изменённые перед этим ставятся в очередь записи (см. «Сохранения»).
- `BlockChanged` получают только игроки, у которых есть этот чанк.
- Позиция из `PlayerMove` проверяется (конечные числа, не дальше 10⁹ блоков): от неё зависит, какие чанки грузить.

**Генерация мира**
- Рельеф строит `TerrainGenerator` по сиду (FastNoiseLite): одинаковый сид — одинаковый мир. Сид и точка появления задаются только при создании мира (`--seed N`, без него — случайный; `--spawn X Z`, по умолчанию над (0, 0)) и дальше хранятся в сохранении. Для уже созданного мира эти аргументы не действуют, сервер пишет об этом в лог.
- FastNoiseLite лежит в `src/Server/ThirdParty/FastNoiseLite.cs` (официального NuGet-пакета нет). Правки относительно оригинала перечислены в начале файла: координаты в `double` (иначе далеко от центра рельеф слипается в ступени) и класс `internal`. При обновлении правки повторить.
- Чанки генерируются в фоновых потоках (`ChunkGenerator`), а в мир попадают только в тике сервера: мир меняет один поток, блокировок на данных мира нет. Игрокам их отправляет подгрузка (`PlayerChunkView`, см. выше), а не сама генерация.
- Ошибка в фоновом потоке не теряется: её пробрасывает следующий тик сервера, а дальше она идёт по цепочке `ServerHost.Fault` → остановка клиента.
- Генератор потокобезопасен, пока шумы только читаются. Настраивать шумы — только в конструкторе.
- **Генерация чанка — чистая функция сида и координат чанка**: никакого общего изменяемого состояния и «дописывания» в соседние чанки. Случайность — только хеш координат с сидом (`TerrainGenerator.Hash`, SplitMix64), не `Random`. Тест `Generation_DoesNotDependOnOrder` строит чанки в разном порядке разными генераторами.
- Деревья (бревно и непрозрачная листва) стоят только на траве. Мир поделён на ячейки 6 × 6 столбцов, в ячейке не больше одного дерева (`TreeInCell` — по хешу ячейки и шуму «лесистости»: леса и поляны). Чанк ставит свои части всех деревьев, чьи кроны его задевают (ищет ячейки с запасом на радиус кроны), листву — только в воздух и раньше стволов, поэтому дерево на границе одинаково с обеих сторон. Новое сооружение, выходящее за чанк, — так же: место и форма по хешу, чанк достраивает свою часть.
- Медная руда — жилы внутри чанка (10 на чанк, по 4–10 блоков), только на месте камня, в том числе в глубоких чанках «сплошного камня».
- Точка появления нового мира обходит деревья: ближайший столбец по спирали, где на высоте тела нет ни ствола, ни листвы (`SpawnColumnNear`).

**Сохранения**
- Мир — один файл SQLite: `%LOCALAPPDATA%\<название игры>\Saves\<имя мира>\world.db` (под Linux — `~/.local/share/<название игры>/Saves/<имя мира>/world.db`), имя мира — аргумент `--world` (по умолчанию `world`). Не в папке сборки: её удаляет `dotnet clean`. Таблицы: `meta` (версия схемы, сид, точка появления, режим нового игрока), `block_names`, `item_names`, `chunks` (позиция → `ChunkCodec`), `players` (имя → позиция, взгляд, режим, выбранный слот, инвентарь, задания). Сохранение от более новой версии схемы не открывается.
- Схема версионируется (`WorldSave.FormatVersion`, сейчас 5). Сохранение старой версии обновляется при открытии, по шагу на версию, каждый — одной транзакцией (`UpgradeFrom1`…`UpgradeFrom4`): новые столбцы добавляются со значениями по умолчанию для старых данных, новая база создаётся сразу с ними. В лог — строка «Сохранение обновлено с формата N до M». Режим мира в версии 1 не записан — это выживание; у игрока из версии 1 — взгляд вдаль, режим мира, пустой инвентарь; у игрока из версий 1–2 — заданий нет; в мирах версий 1–3 предметов на земле нет (таблица `entities` появляется пустой); у игрока из версий 1–4 здоровье полное (столбец `health`, NULL — полное, 0 — погиб и вышел, не возродившись: при входе он в точке появления с полным здоровьем).
- **Сущности в сохранении** (с шага 7.4) — вместе со своими чанками: таблица `entities` (позиция чанка → двоичный блок `EntityCodec`), чанк без сущностей в ней не хранится. Блок: байт версии, число сущностей, у каждой — имя вида, длина данных и данные (длина позволяет пропустить неизвестный вид — сущность удалённого мода — не испортив соседние). Вид `item`: позиция, скорость, опора, номер предмета в сохранении, число штук, задержка подбора, возраст. Неизвестный предмет пропадает, стопка больше предела урезается, испорченный блок — строка в лог и пустой чанк.
- Кто пишет и читает сущности — `EntityPersistence`: сервер выгружает чанк — его сущности записываются и убираются из памяти (`World.Unload` возвращает выгруженные позиции); автосохранение и выход записывают все и стирают опустевшие чанки. Читаются они в фоновом потоке вместе с чанком (`World.Produce` → `TryLoadEntities`, сначала очередь записи) и появляются в тике, когда чанк уже в мире (`World.TryTakeLoadedEntities`). Чей чанк — по точке сущности в момент записи. Если в загружаемом чанке уже есть живые сущности (созданы в незагруженном месте), строка не восстанавливается — правда в памяти, иначе было бы удвоение.
- Задания игрока — JSON-текст `QuestCodec` (`{"version": 1, "completed": [имена], "progress": {имя: число}}`): заданий немного, а имена видны прямо в базе. Хранятся имена, поэтому выполненное задание мода, которого сейчас нет, сохраняется и вернётся с модом. `Decode` проверяет версию, имена и числа; испорченные задания пишутся в лог и начинаются заново, остальное у игрока сохраняется.
- Сохраняется каждый сгенерированный чанк, а не только изменённые: генератор будет меняться, и нетронутые места не должны пересоздаваться по-новому рядом с постройками. Свежий чанк сохраняет фоновый поток генерации сразу после генерации. Изменённый («грязный», `World.TrySetBlock`) — сервер при выгрузке, при автосохранении раз в минуту и при выходе. Менять блоки на сервере — только через `World.TrySetBlock`, иначе изменение не попадёт на диск.
- Чанки и инвентари на диске хранятся в номерах сохранения, а не реестра: перевод по именам — `NameIdMap` (для чанков — обёртка `BlockIdMap`), таблицы `block_names` и `item_names`. Таблицы только растут: новое имя получает следующий номер, старые не меняются. Блок, которого больше нет в реестре, при загрузке становится воздухом, предмет — пустым слотом (с предупреждением в логе), но имя остаётся в таблице.
- Инвентарь игрока — двоичный блок `InventoryCodec`: байт версии, число непустых слотов, для каждого — слот, номер предмета в сохранении и число штук (числа по 7 бит в байте). Курсор записывается как слот 36; при входе сервер возвращает его предмет в инвентарь (`Inventory.ReturnCursor`), а что не влезло — остаётся на курсоре. `Decode` проверяет данные с диска; испорченный инвентарь пишется в лог и становится пустым (позиция и остальное сохраняются), стопка больше предела урезается до него.
- Диск пишет один поток (`WorldSave`): остальные только ставят данные в очередь, а он пишет накопившееся одной транзакцией. Тик сервера диск не ждёт. Чанк из очереди, ещё не записанный на диск, загрузка берёт из памяти: иначе быстро выгруженный и снова запрошенный чанк вернулся бы старым.
- Читают сохранение фоновые потоки генерации (`World.Produce`): сначала сохранение, нет там чанка — генерация. У каждого потока своё соединение, режим WAL позволяет читать во время записи. Испорченный чанк пишется в лог и генерируется заново.
- Если поток записи упал, следующий тик сервера бросает исключение (`ThrowIfFaulted`): играть дальше, молча ничего не сохраняя, нельзя.
- При выходе `GameServer.Dispose` останавливает генерацию, ставит в очередь изменённые чанки и игроков и ждёт, пока всё будет записано. Поэтому сервер освобождается после остановки его потока. Игроки записываются и при автосохранении.
- Игрок продолжает там, где вышел: позиция, взгляд, режим (`JoinAccepted`), инвентарь и выбранный слот (`InventoryContents`), задания (`QuestBookContents`). Новый игрок — в точке появления, взгляд вдоль −Z, режим мира, пустой инвентарь. Игроки в сохранении различаются по имени.

**Физика игрока**
- Физика — в Shared (`Shared.Physics`), одна для клиента и сервера: `PlayerPhysics.Step(состояние, ввод, мир)` — чистая функция без случайностей и времени кадра, шаг всегда равен тику. Направление движения в `PlayerInput` — уже в мировых осях: физика ничего не знает о камере.
- Позиция тела — точка ног. Тело — короб 0,6 × 1,8 × 0,6, глаз на 1,62.
- Столкновения — короб против полных кубов твёрдых блоков (`BlockRegistry.IsSolid`; id не из реестра считается твёрдым). Перемещение обрезается по осям Y, X, Z; блоки берутся из короба «тело + весь путь за тик», поэтому на любой скорости тело не проскакивает сквозь стену.
- Сравнения коробов — с допуском `Aabb.Epsilon` (10⁻⁶): после сложения double тело у стены может оказаться на 10⁻¹⁰ внутри неё, и без допуска стена перестала бы держать. Блок, в который тело уже вошло, движение не останавливает: застрявший может выйти.
- Если тело за тик задело бы незагруженный чанк, оно стоит на месте и теряет скорость: иначе игрок провалился бы сквозь ещё не пришедший мир.
- Клиент двигает игрока сам (`PlayerController`) и шлёт в `PlayerMove` точку ног; сервер хранит её же. Глаз — на `PlayerPhysics.EyeHeight` выше: точку взгляда из `UseItem` сервер сравнивает с глазом, а не с ногами.
- Сервер проверяет каждое `PlayerMove` (`MovementCheck`): путь тела от прошлой принятой позиции (`PlayerPhysics.Sweep`) не должен обрезаться о блоки, а перемещение — превышать «запас пути» (пополняется каждый тик на предельную скорость режима, копится до 10 тиков). Пределы — `MovementLimits`: в выживании 5,6 блока/с по горизонтали (бег) и 9,8 вверх (прыжок), в творческом 22 и 22 (быстрый полёт), вниз в обоих 78. Нарушение — игрок возвращается назад сообщением `PlayerTeleport` с новым номером; `PlayerMove` со старым номером (отправленные до телепорта) игнорируются. Отклонение пишется в лог сервера.
- `PlayerMove` несёт и направление взгляда (`LookAngles`); клиент шлёт его, когда меняется позиция или взгляд. Взгляд сервер не проверяет (он нужен только для сохранения), лишь отбрасывает NaN и нормализует углы.
- Переносить игрока на сервере — только `GameServer.Teleport` (он же шлёт `PlayerTeleport`): прямое присваивание позиции рассинхронизирует клиента. Тесты, которым нужно поставить игрока далеко, телепортируют его (`TestServers.Teleport`), а не шлют `PlayerMove`.
- Твёрдый блок не ставится, если пересекает тело любого игрока (`IWorld.IsBlockedByPlayer`).
- Полёт — со столкновениями. Чтобы пролететь далеко по прямой, нужно подняться выше гор (поверхность — до y = 192).

**Режимы игры**
- Режим (`GameMode`: выживание или творческий) — свойство игрока, хранится в сохранении. Новый игрок получает режим мира по умолчанию: `--mode survival|creative` при создании мира (по умолчанию выживание), дальше он в `meta`. В сохранении режим — имя (`GameModes.ToName`), а не номер.
- Режим меняет только сервер: клиент по G шлёт `SetGameMode`, сервер отвечает `GameModeChanged`. Прав доступа пока нет — сервер разрешает смену всем (временно, до команд). Менять режим на сервере — только через `ChangeMode` (вместе с ним меняются пределы движения; для тестов — `GameServer.SetGameMode`).
- При переходе в выживание сервер сразу шлёт `PlayerTeleport` на текущее место: клиент ещё тик-другой летит по-творчески, и его перемещения, уже посчитанные по старым пределам, становятся устаревшими (старый номер телепорта), а скорость полёта у клиента гаснет. Запас пути, накопленный в творческом, урезает до нового предела первое же пополнение (`MovementCheck.Refill`).
- Летать (F) можно только в творческом; клиент, узнав о переходе в выживание, выключает полёт.
- В творческом предметы бесконечные: ломание не роняет добычи, установка ничего не тратит (`ItemUseContext.InfiniteItems`), лежащие предметы не притягиваются и не подбираются. Выбросить (Q) можно и в творческом.

**Предметы и действия игрока**
- Предметы — отдельно от блоков: `ItemId` и `ItemRegistry` в Shared (имена, заморозка, id по порядку регистрации — как у блоков). Каждый блок, кроме воздуха, регистрирует одноимённый предмет, который его ставит (`ItemDefinition.Block`); он же — добыча с блока (`ItemRegistry.ForBlock`). Предел стопки — свойство предмета (64 для блоков).
- Предмет с id 0 — «воздух», то есть «ничего». Пустая стопка одна: `ItemStack.Empty` = `default` = воздух ×0; конструктор `ItemStack` сводит к ней «камень ×0» и «воздух ×5».
- Кнопки мыши означают не «сломать/поставить», а действия предмета в руке: основное (ЛКМ) и дополнительное (ПКМ). Клиент шлёт `UseItem(действие, точка взгляда, направление)`, а что произойдёт, решает сервер по поведению предмета (`Api.IItemBehavior`). Поведение предмет называет по имени — поле `behavior` в JSON; по умолчанию `base:place_block` (предмет-блок ломает и ставит, `BlockItemBehavior`) или `base:hand` (пустая рука и предметы без своего поведения только ломают, `HandBehavior`). Новый вид предмета (инструмент, еда, оружие) — новая реализация `IItemBehavior` в моде, без новых сообщений и без правок клиента.
- Сервер не верит клиенту на слово: повторяет луч по своей копии мира и проверяет, что точка взгляда рядом с известной ему позицией игрока.
- Блоки на сервере меняются только через одну точку (`IWorld`, реализация — `GameServer.WorldEditor`), которая сразу рассылает `BlockChanged` игрокам, у которых есть этот чанк.
- **Добыча падает предметом** (с шага 7.3; до него клалась сразу в инвентарь, а при полном инвентаре блок не ломался). Сломанный блок ломается всегда, добыча (`GameServer.FinishBreaking`) появляется предметом на земле в центре блока с небольшим разлётом (`ItemEntities.SpawnDrop`). Подбирает её игрок в выживании (`ItemSystem`): сначала доливаются неполные стопки того же предмета, потом занимается первый пустой слот, и там и там хотбар раньше основной части; что не влезло, лежит дальше. Поставленный блок тратит одну штуку из руки; последняя освобождает слот. Так — в выживании; в творческом см. «Режимы игры».
- **Предметы на земле** (`ItemSystem`, по порядку в тике: старение → притяжение → движение → подбор → слияние). Задержка подбора: добыча — 0,5 с, выброшенное — 2 с. Предмет, который можно подобрать, летит к ближайшему игроку в выживании (3 блока от тела, 8 блоков/с), если тому есть куда его положить; касание тела (с запасом 0,3) — подбор и событие модов `ItemPickedUp`. Одинаковые предметы ближе 0,5 блока сливаются до предела стопки (живут по младшему, ждут по большей задержке). Слияние — раз в 10 тиков (`MergeIntervalTicks`). Через 5 минут предмет исчезает. Ни одна из систем не создаёт и не теряет штук — это проверяет тест сохранения количества. Моды кладут предметы через `IWorld.SpawnItem`.
- Выбросить: Q — одну штуку, Ctrl+Q — стопку (`DropItem`); закрытие экрана инвентаря возвращает курсор в слоты, а не влезшее выбрасывает (`ReturnCursorOrThrow`) — на невидимом курсоре ничего не остаётся.
- **Ломание удержанием** (с шага 6.3). ЛКМ у руки, инструментов и предметов-блоков начинает ломание (`ItemUseContext.Breaker.StartBreaking`); время в тиках считает сервер (`Mining.BreakTicks`) и ломает блок, когда оно прошло, — клиент не может ломать быстрее. Ломание отменяется, если клиент прислал `StopBreaking` (отпустил ЛКМ, прицел ушёл в пустоту, открыт инвентарь), сменился выбранный слот или предмет, блок на месте стал другим или игрок ушёл дальше досягаемости. В творческом и у блока с нулевой твёрдостью — сразу. Клиент в выживании сам переходит к следующему блоку, пока ЛКМ держат (новое основное действие при смене цели, предмета или блока); в творческом удержание ЛКМ повторяет действие раз в 0,2 с (`ButtonRepeat`).
- **Время и добыча** — `Shared.Items.Mining`, одна формула для сервера и клиента: подходящий инструмент (вид совпадает с `tool` блока) делит `hardness` на свою скорость; если уровня инструмента не хватает до `toolTier`, ломание в 10/3 раза медленнее и без добычи (камень рукой 7,5 с и пусто).
- Трещины рисует клиент (`CrackRenderer`, шейдер `crack`): 10 стадий из `Assets/Textures/Effects/destroy_N.png` — слои массива текстур после картинок предметов; куб чуть больше блока, без записи глубины. Только у предметов с поведением `base:hand` или `base:place_block`: у предмета со своим поведением ЛКМ значит другое.
- **Ремесло** (с шага 6.4). Клиент шлёт только `CraftRecipe(имя рецепта, все)`; сервер сам проверяет ингредиенты, станок и место (`GameServer.HandleCraft`) и присылает изменённые слоты. Невыполнимая просьба молча пропускается (клиент мог показать рецепт по чуть устаревшему инвентарю), неизвестное имя — строка в лог. Shift+клик повторяет, пока получается; событие `ItemCrafted` — одно на действие, с числом повторов.
- Трата и выдача — одним обменом `Inventory.TryExchange`: целиком или никак. Ингредиенты берутся из основной части, потом из хотбара (то, что под рукой, остаётся), курсор не считается; результат кладётся как добыча. Место под результат считается после траты: последние доски, ушедшие на верстак, освобождают ему слот. Не поместилось — откат слотов и отметок изменений, клиенту ничего не уходит.
- Станок — обычный блок, на который ссылается рецепт (`station`); рядом — ближайшая точка его куба не дальше `Crafting.StationReach` от глаза; это та же досягаемость, что у блока (`GameRules.BlockReach`, 6): поставленным станком можно сразу пользоваться (на шаге 6.4 было 4 — при прохождении верстак в конце туннеля оказывался «не рядом»). Правила ремесла — `Shared.Items.Crafting`, одни для сервера (решает) и клиента (показывает доступность).
- **Задания** (с шага 6.5). Определения — `Quest` (цель `QuestGoal`: иметь, сделать, сломать, поставить — с числом; предшествующие задания), реестр `QuestRegistry` упорядочен по глубине цепочки, затем по имени — требуемое задание всегда раньше требующего. Состояние игрока — `QuestBook` (выполненные и набранное), одно для сервера (авторитетная копия, сохранение) и клиента (журнал, подсказки). Ведёт задания `QuestTracker` на сервере, и только в выживании. Считаемые цели («сделать», «сломать», «поставить») вызываются прямо из единственных точек действия — `HandleCraft` и `WorldEditor.TryBreakBlock`/`TryPlaceBlock` (значит, и у поведений модов), а не через события модов: подписки замораживаются раньше, чем появляется `WorldEditor`. Действие засчитывается заданиям, доступным до него: открытое этим же действием начинает счёт со следующего. «Иметь предмет» проверяется по инвентарю в конце каждого тика — одним проходом по реестру, которого хватает и на цепочки. Клиенту — `QuestBookContents` при входе и `QuestChanged` при каждом изменении; модам — событие `QuestCompleted`.
- Инвентарь (`Inventory`, Shared): 36 слотов — 0–8 хотбар, 9–35 основная часть; номер 36 — предмет на курсоре (`CursorSlot`), он тоже на сервере. Авторитетная копия — на сервере. Клиент меняет только выбор слота (1–9, колесо) и сообщает его `SelectHotbarSlot` — но лишь после того, как получил `InventoryContents`: иначе пришедший инвентарь вернул бы клиенту прежний слот, а сервер держал бы в руке другой. Остальное — намерения (`InventoryClick`: слот и вид клика), которые сервер применяет тем же кодом `Inventory.Click`. Клиент не может «нарисовать» себе предметы.
- Слоты инвентаря меняются только через `Inventory.Put`: он запоминает изменённые слоты. Сервер в конце тика забирает их (`TakeChanges`) и шлёт одним `InventoryChanged`; при входе — весь инвентарь (`InventoryContents`) сразу за `JoinAccepted`.

**Интерфейс**
- Свой 2D-интерфейс в `Engine.Ui`. Геометрию за кадр собирает `UiCanvas` (без OpenGL, проверяется тестами): четырёхугольники в пикселях экрана, (0, 0) — левый верхний угол, порядок добавления — порядок наложения. Рисует её `SpriteBatch` одним вызовом, без глубины и отсечения граней; его шейдеры встроены в сборку Engine.
- Две текстуры подключены сразу: атлас интерфейса (`UiAtlas`: глифы и белый квадрат для заливки, покрытие — в альфе, цвет — из вершины) и массив текстур блоков (иконки). Источник выбирает слой вершины: −1 — атлас, иначе слой массива. Поэтому иконки, текст и рамки можно смешивать в любом порядке без лишних вызовов. Из массива интерфейс берёт нулевой уровень mip-карт: иконка рисуется пиксель в пиксель.
- Масштаб интерфейса — только целый (`UiScale`): наибольший, при котором в окно помещается 320 × 240 пикселей интерфейса (1280 × 720 → 3, 1920 × 1080 → 4). Все размеры и положения интерфейса — целые пиксели экрана (`HudLayout`).
- Шрифт — `Assets/Fonts/ui.ttf` (сейчас Press Start 2P, лицензия OFL рядом в `OFL.txt`); заменить шрифт — заменить файл. Атлас растеризуется под масштаб (`UiAtlas.Build`, StbTrueTypeSharp), глифы ложатся на экран пиксель в пиксель, без растягивания. Размер текста задаётся высотой прописной — **высотой контура «H»** (7 пикселей интерфейса), а не кеглем и не верхом контура: у Press Start 2P буквы стоят на клетку выше базовой линии, и по верху сетка шрифта не легла бы на пиксели. Положение каждого глифа округляется до целого пикселя, перо копится дробным.
- Атлас строится при загрузке (`Hud`), а не в первом кадре: первое построение с компиляцией кода растеризации — около 22 мс; перестройка при смене масштаба (изменили размер окна) — 3–8 мс.
- Иконка блока — изометрический кубик из массива текстур блоков (`ItemIcons`): верх, южная грань слева, восточная справа, яркость граней как в мире (`BlockFace.Brightness`). Новый блок получает иконку сам.
- Картинка предмета — поле `icon` в JSON (полное имя `пакет:имя`, короткое дополняется пакетом), файл `Assets/Textures/Items/<имя>.png` у игры или `textures/items/<имя>.png` у мода (`TextureFiles`). Картинки предметов — слои того же массива текстур, что и блоки, сразу после них (`ItemVisuals`); предмет с картинкой рисуется плоским квадратом её слоя, предмет-блок без картинки — кубиком, остальные — «нет текстуры». Все слои массива — 16×16: файл другого размера или без файла заменяется шахматкой с записью в лог, игра не падает.
- Названия предметов для игрока — поле `displayName` в JSON предмета (`ContentRegistries.ItemDisplayNames` → `ItemNames` на клиенте); без названия показывается постоянное имя (`mod:item`). Переводы — позже.
- Экран инвентаря (E): справа от инвентаря — панель «РЕМЕСЛО», сетка 4 столбца, той же высоты, что панель инвентаря. Высота панели инвентаря — по числу строк творческой палитры (в выживании палитры нет); обе панели вместе стоят по центру экрана и при трёх строках палитры (296 × 198) помещаются в 320 × 240 пикселей интерфейса. Список (`RecipeList`): доступные сейчас — сверху, остальные затемнены, внутри групп — порядок реестра; колесо над панелью прокручивает строки. Подсказка рецепта — что получится, «есть/нужно» по каждому ингредиенту и станок (зелёным или красным). Клик попадает в список, нарисованный в прошлом кадре: игрок жмёт на то, что видел. Геометрия — статические методы `InventoryScreen` (проверяются тестами без окна).
- Задания в интерфейсе (`QuestView` — иконка цели, счёт, порядок, перенос текста; без OpenGL, проверяется тестами): в левом верхнем углу — до трёх доступных заданий со счётом (только в выживании); в правом верхнем — уведомление «Задание выполнено!» на 4 с (`ToastQueue`: по очереди, каждое — полное время, последние полсекунды гаснет), рисуется последним, поверх экранов; журнал (J, `JournalScreen`, 304 × 216) — доступные со счётом и описанием в две строки, под ними выполненные зелёным, недоступные только числом «впереди ещё N», колесо прокручивает.
- Перекрестие — часть интерфейса (`HudLayout.Crosshair`), рисуется с инверсией фона (`UiBlend.Invert`); черты не перекрываются, иначе двойная инверсия вернула бы в центре цвет фона.

**Контент**
- Блоки и предметы описываются JSON-файлами в `content/<пакет>/` (один файл — одно определение; ванильные — `content/base/blocks/*.json` и `content/base/items/*.json`). Сервер и клиент грузят их одинаково: `GameContent.Load()` читает все пакеты из `Content/` рядом с exe через `ContentLoader`. Блоков и предметов в коде не регистрируем.
- **Пакет = папка верхнего уровня = пространство имён.** Пакет `base` объявляет только `base:…`; ссылаться (`placesBlock`) может на любые имена. Имя пакета — a–z, 0–9, _; JSON в корне контента, вне папки пакета, — ошибка. Поэтому два пакета не могут занять одно имя, а по имени видно, кто его объявил. Переопределение чужих определений (мод меняет `base:stone`) пока невозможно — решать на этапе 5.
- Корней контента может быть несколько (`ContentLoader.LoadDirectories`): игра, позже папка модов. Пакет с одним именем в двух корнях — ошибка с обоими путями.
- Ошибка контента при запуске — одна строка `[Content] Ошибка в контенте игры: Файл '<пакет>/…': …` в stderr и код выхода 1 (`Program.CreateServer`); окно не открывается.
- Блок: `type: "block"`, `name`, `isOpaque`, `isSolid` (по умолчанию `true`), `textures` — строка (одна текстура на все грани) или объект `top`/`side`/`bottom`. Предмет: `type: "item"`, `name`, `maxStackSize`, `placesBlock` (необязательно). Имена — `namespace:name` (a–z, 0–9, _), имена текстур — a–z, 0–9, _ (без путей). Неизвестное или повторённое поле, неверный тип, ссылка на несуществующий блок — ошибка загрузки (`ContentLoadException`) с путём файла; игра с ошибочным контентом не запускается. Ломание: `light` (собственный свет 0–15, по умолчанию 0), `hardness` (секунды рукой, если добывается рукой; по умолчанию 1; 0 — сразу), `tool` (вид инструмента: `pickaxe`, `axe`, `shovel` или свой) и `toolTier` (нужный уровень; без `tool` — ошибка). Предмет-инструмент: `tool: {type, tier, speed}`, поведение по умолчанию — `base:hand` (ломает как рука, только быстрее). Рецепт: `type: "recipe"`, `name`, `result` и `ingredients` — стопки `{item, count}` (`count` по умолчанию 1), необязательный `station` — блок. Ссылки рецепта проверяются после всех блоков и предметов (с заменами): неизвестный предмет или станок, результат больше стопки, повтор ингредиента — ошибка загрузки. Имена рецептов — отдельные от предметов (рецепт `base:planks` и предмет `base:planks` не мешают друг другу); реестр — `ContentRegistries.Recipes`, по порядку имён. Задание: `type: "quest"`, `name`, `title`, `description`, `goal` (`{type: obtain|craft, item}` или `{type: break|place, block}`, `count` по умолчанию 1), `requires` — имена заданий. Проверяются после всего контента: цель на существующий предмет или блок, требования существуют, без себя, повторов и кругов (сообщение называет круг); реестр — `ContentRegistries.Quests`.
- Имена текстур в `textures` полные: `пакет:имя`. Короткое имя дополняется пакетом, где описан блок (`"stone"` в `base` → `base:stone`), поэтому текстуры разных модов не сталкиваются. Файл по имени ищет клиент (`TextureFiles`): у мода — `textures/blocks/<имя>.png` в его папке, у пакетов игры — `Assets/Textures/Blocks/<имя>.png`.
- **Явная замена:** определение с `"override": true` целиком заменяет одноимённое определение того же типа (блок, предмет, рецепт, задание) из чужого пакета. Заменять можно только существующее и только у пакета, от которого мод зависит (транзитивно); если одно имя заменяют несколько модов, каждый следующий по порядку должен зависеть от предыдущего — побеждает последний; независимые замены одного имени — ошибка. Без флага чужое пространство имён — по-прежнему ошибка. Имя не меняется, поэтому сохранения не затрагиваются; стопка больше нового предела урезается при загрузке (`InventoryCodec`).
- Пакет мода — его id и папка `content/` мода (`GameContent.Load(mods)` добавляет их к пакетам из `Content/`); загрузчику пакеты передаются парами «имя → папка» (`ContentPack`, `ContentLoader.LoadPacks`).
- Числовые id назначаются по именам в ordinal-порядке (воздух — 0), а не по порядку файлов: у сервера и клиента они совпадают сами (клиент всё равно сверяет имена при подключении). Долговременная идентичность — строковое имя: сохранения хранят таблицы имён, поэтому новый блок, сдвигающий числовые id, старые миры не ломает (проверено вживую на шаге 4.2).
- Код, которому нужны конкретные ванильные блоки (генератор мира), получает их id по имени через `BaseBlocks.From(registry)`; нет блока — `KeyNotFoundException` при запуске.
- Тесты, которым нужны «блоки как в игре», берут настоящий контент (`GameContent.Load()`). `GameContentTests` фиксирует ванильные блоки, их свойства, текстуры и предметы; `BlockVisualsTests.ContentTextures_AllHaveFiles` — что у каждой текстуры из JSON есть файл.

**Моды**
- Публичный API модов — проект `src/Api`; внутренние типы сервера остаются `internal`, наружу — только узкие интерфейсы (`IWorld`, `IPlayer`). Новую возможность для модов добавляем в Api, а не открываем внутренности.
- Мод — класс `IMod`; в `Load(IModContext)` он регистрирует поведения предметов (`RegisterItemBehavior`) под именами своего пространства имён (`<id мода>:…`). После загрузки модов `ItemBehaviorRegistry.Bind` связывает каждый предмет с поведением (массив по `ItemId`), реестр замораживается; ссылка на незарегистрированное поведение — ошибка контента при запуске.
- Моды лежат в общей папке `Mods/` в данных игры (`%LOCALAPPDATA%\<название игры>\Mods`, Linux: `~/.local/share/<название игры>/Mods`), по папке на мод; `--mods ПАПКА` подменяет её (`playtest.sh` по умолчанию даёт пустую). Мод — `mod.json` (`id` = имя папки = пакет = пространство имён; `name`, `version`, `dependencies` «id → наименьшая версия», `assembly` — имя DLL в папке), `content/` и `textures/blocks/`. Встроенный мод `base` (версия 1.0.0) в папке не лежит, но зависеть от него можно.
- Порядок загрузки — по зависимостям, при прочих равных по id (`ModDiscovery.Order`); нет зависимости, мала версия, цикл — ошибка запуска. Любая ошибка мода (манифест, зависимости, сборка, исключение в `IMod.Load`) — `ModLoadException` с id мода, при запуске одна строка `[Mods] …` и код выхода 1.
- Сборка мода грузится в свой `AssemblyLoadContext` (`ModAssemblies`); сборки Api и Shared всегда берутся из игры, иначе `IMod` мода и игры были бы разными типами. В сборке ровно один класс `IMod` с открытым конструктором без параметров. Проект мода ссылается на Api и Shared с `Private="false"` и `ExcludeAssets="runtime"` — в папку мода они не копируются (см. `examples/ExampleMod`).
- Мир запоминает моды, с которыми его открывали (`meta.mods`: id → версия), и при открытии без какого-то из них пишет в лог, что его блоки станут воздухом, а предметы пропадут.
- Мод видит все задания (`IModContext.Quests`) и добавляет свои данными — `type: "quest"`, в том числе продолжающие ванильную цепочку (`requires` на любое задание).
- Мод видит все рецепты (`IModContext.Recipes`) и добавляет свои данными — `type: "recipe"` в своём `content/`; предметы и станки — любых модов.
- Ванильное поведение — встроенный мод `BaseMod` (id `base`), подключается тем же `IModContext`, что и сторонние. Своих путей для ванили в обход API нет.
- События мира (`IModContext.Events`): `BlockBroken`, `BlockPlaced`, `PlayerJoined`, `ItemCrafted`, `QuestCompleted` — уже случившиеся, без отмены. Ломание и установка игроком идут через `IWorld.TryBreakBlock` / `TryPlaceBlock` — они и поднимают события, поэтому поведение любого мода, ломающее через них, порождает события так же, как ванильное; `TrySetBlock` меняет блок без событий (правки мира, не действие игрока).
- События не вызываются на месте: `GameEvents` ставит их в очередь, а сервер разбирает её после каждого сообщения клиента (`Dispatch`). Обработчик видит действие законченным (добыча уже в инвентаре); события, поднятые обработчиками, разбираются там же, но не больше `MaxEventsPerDispatch` (10 000) за раз — бесконечная цепочка модов обрывается с записью в лог. Исключение обработчика пишется в лог с id мода и не мешает игре и другим обработчикам. Подписка — только в `IMod.Load`.

**Сущности** (с шага 7.1)
- Всё, что движется и не является блоком (предметы на земле, позже мобы и снаряды), — сущности своего ядра ECS `Shared.Entities`. Сущность — только номер `EntityId` (индекс + поколение), данные — компоненты-структуры в `ComponentStore<T>` (sparse set: значения подряд в памяти), поведение — системы сервера, которые обходят `EntityWorld.Query<…>()` по 1–3 компонентам.
- Хранить чужую сущность — только по `EntityId` и проверять `IsAlive`: индекс удалённой достаётся новой, а поколение отличает их.
- Удаление отложенное: `Destroy` сразу делает сущность мёртвой (запросы её не видят), компоненты и индекс освобождает `FlushDestroyed` — последним действием `GameServer.Tick`. Внутри обхода запроса можно удалять сущности и компоненты и создавать новые (новые в этот обход не попадают). Ссылка из `Get<T>` действует до следующего добавления или удаления компонента этого типа — не держать её через `Set`/`Create`.
- Мир сущностей — `GameServer.Entities`, только на сервере и только в его потоке. Системы вызываются в `Tick` по порядку в одном месте: после действий игроков и ломания, до рассылки чанков.
- Обход запроса не выделяет память (снимок номеров — из `ArrayPool`); замер 7.1: проход по 10 000 сущностям с записью — 0,14 мс в Release, 0,66 мс в Debug.
- Физика тел — одна для всех (с шага 7.2): `BoxPhysics.Move` (короб против блоков, по осям Y, X, Z) считает и игрока (`PlayerPhysics`), и сущности; падающее тело — `BoxPhysics.Fall` с формой `BodyShape` (размер, гравитация, сопротивление воздуха, трение о землю). Путь в незагруженный чанк — тело стоит на месте без скорости. Лежащее тело (на опоре, без скорости) не пересчитывается, пока под ним твёрдый блок (`HasSupport`; касание соседнего столбца гранью — не опора): тысяча лежащих предметов иначе стоила полмиллисекунды тика.
- Компоненты сервера — `Server.Entities` (`Position`, `Body`, `DroppedItem`, `Synced`). Порядок в `Tick`: действия игроков → ломание → `MovementSystem` → рассылка чанков → `EntitySync` → … → `FlushDestroyed`.
- Клиент знает сущность, пока у него есть её чанк (как с `BlockChanged`): `EntitySpawned` — когда она в отправленном чанке впервые (после самого `ChunkData`), `EntitiesMoved` — одним сообщением за тик только сдвинувшиеся (`Synced.SentPosition`), `EntityRemoved` — удалена или чанк ушёл. Известные клиенту — `ClientSession.KnownEntities`. Номер сущности в сообщениях — серверный `EntityId`.
- Клиент сущностями не управляет: `ClientEntities` хранит два последних положения (сообщения разбираются в начале тика клиента) и рисует между ними по доле тика, как камеру.
- Предметы на земле рисуются одним вызовом (`ItemEntityRenderer`, шейдер `item`): общий меш «кубик + квадрат», по экземпляру на предмет (instancing, `VertexArrayObject.SetBindingDivisor`); ненужная экземпляру часть меша уводится за экран в шейдере. Предмет-блок без картинки — вращающийся кубик (слои верха, бока, низа), предмет с картинкой — картинка, повёрнутая к камере по горизонтали; оба покачиваются. Вид — `ItemLook.For`, как у иконок интерфейса.

**Здоровье и смерть** (с шага 7.5)
- Игрок — тоже сущность: при входе создаётся `ClientSession.Entity` с `Position` (каждый тик повторяет принятую позицию), `Health` и `Fall`. Остальные системы его не трогают: у него нет `Body` и `DroppedItem`.
- Здоровье — 20 единиц (`PlayerHealth`), клиенту — `HealthChanged` при входе и каждом изменении. Восстановление — единица за 4 с у живого (с урона отсчёт заново). Урон — только в выживании, через `GameServer.Damage(игрок, сколько, причина)`; причина — имя вида `base:fall`; событие модов `PlayerDamaged`.
- Урон от падения считает сервер по принятым позициям (`TrackFall`): самая высокая точка ног с последнего касания земли (чуть ниже ног — твёрдый блок), урон — каждый целый блок сверх 3 (`PlayerHealth.FallDamage`: 3 — ноль, 10 — семь). В творческом урона нет (это решает `Damage`, для любой причины); любой телепорт сервера (отклонённое движение, смена режима, возрождение) сбрасывает её — перенос не падение.
- Смерть (здоровье 0): весь инвентарь и курсор выпадают предметами на месте с задержкой подбора броска, клиенту — `DeathNotice(причина)`, событие `PlayerDied` (вещи уже выпали). До `Respawn` от клиента сервер молча пропускает все сообщения погибшего (движение, действия, клики) и он ничего не подбирает. Возрождение — в точке появления мира с полным здоровьем (телепорт + `HealthChanged`).
- Клиент: полоса здоровья над левым краем хотбара (только в выживании; по 4 пикселя интерфейса на единицу — край заливки чёткий; название предмета в руке поднято выше полосы), экран смерти (`Hud.DrawDeath`: затемнение, «Вы погибли!», причина текстом `DeathCauses`, кнопка «Возродиться» — клик или Enter); на экране смерти обычный интерфейс скрыт, курсор отпущен. Здоровье видно и в заголовке окна.

**Свет** (с шага 8.1)
- Свет — `Shared.Lighting`, два канала по 4 бита в байте на блок (`ChunkLight`, `Chunk.Light`): небесный (старшие биты) и блочный, 0–15. Пока весь чанк освещён одинаково, массива нет — одно значение (так у 1364 чанков из 1639 при входе); массив заводится при первой отличающейся записи.
- Правило (`LightEngine`): непрозрачный блок света не пропускает — небо 0, блочный свет равен его собственному свечению (`light` в JSON, `BlockDefinition.Light`); в прозрачном — наибольшее из своего свечения и света соседей минус один; небесный 15 идёт вниз без потерь. Результат — наименьший свет по этому правилу и не зависит от порядка правок: тесты сверяют его с расчётом «с нуля» после случайных правок, прихода и ухода чанков.
- Кто меняет мир, тот сообщает движку: `ChunkAdded` (чанк уже в `ChunkMap`), `ChunkRemoved` (уже убран), `BlockChanged` (блок уже стоит). Заменить загруженный чанк — сначала `ChunkRemoved`. Чьё освещение изменилось — `TakeChanged`. Движок однопоточный, работает в потоке, который меняет мир.
- Новый чанк: солнце по столбцам без очереди (до первого непрозрачного), в очередь — только край освещённого; верхний слой чанка снизу пересчитывается только там, где столб солнца оборвался. Иначе каждый чанк воздуха сверху перезаливал бы все столбы под собой (замер шага 8.1: 7 мс на чанк воздуха вместо 0,2).
- Солнце над незагруженным чанком — `ISkyAbove`: на сервере `NaturalSky` — открыто выше естественной высоты столбца (рельеф и деревья по генератору, `TerrainGenerator.NaturalTops`, кеш по столбцам чанков), в тестах `OpenSky` или своя высота. Незагруженные соседи света не дают и не получают. Естественную высоту считают заранее потоки генерации (`NaturalSky.Prepare` в `World.Produce`), тик только читает кеш.
- Уход чанка (`ChunkRemoved(Chunk)` — движку нужен последний свет ушедшего) снимает у соседей только свет, который мог прийти из него (то же правило зависимости, что в заливке); блоки, чей собственный свет не меньше прежнего, не трогаются. Снимать все граничные блоки подряд нельзя: столб солнца у соседа сбоку снимался бы до земли и заливался заново — в полёте выгрузка стоила до 0,9 с (шаг 8.2). Уходят несколько — сначала все из `ChunkMap`, потом `ChunkRemoved` для каждого: стороны между ушедшими пропускаются.
- **Свет на сервере** (с шага 8.2) живёт в мире: `World.Light`. `World` сам сообщает движку о приходе чанка (`CollectGenerated`), выгрузке (`Unload`) и смене блока (`TrySetBlock`) — поэтому менять блоки и чанки на сервере можно только через `World`. Приход чанков за тик ограничен бюджетом `World.CollectBudgetMs` (15 мс, хотя бы один чанк): готовых за тик бывает до 64, и тик со светом доходил до 80 мс; что не уложилось, ждёт в очереди готовых.
- **Свет у клиента**: клиент свет не считает. Он приходит в `ChunkData`, а изменения — сообщением `ChunkLightChanged` (весь свет чанка заново): сервер забирает изменившиеся чанки (`TakeChanged`) дважды за тик — до рассылки чанков (новые чанки и так несут свежий свет) и в конце тика (выгрузка, обработчики модов) — и шлёт их тем, у кого чанк уже есть, в том же тике, что и причина. После каждого тика свет у клиента равен свету сервера — это проверяет `LightSyncTests` клиентом, собранным только из сообщений. Клиент хранит свет в чанке (`ClientWorld.SetLight`) и строит по нему меши (с шага 8.3, см. «Рендер»).

**Игровой цикл**
- Логика идёт фиксированными тиками: 20 TPS (`Shared.GameTime`), независимо от FPS. Длинные кадры (больше 0,25 с) обрезаются, чтобы игра не пыталась догнать время сотнями тиков подряд.
- Рендер интерполирует между двумя последними состояниями: `Lerp(previous, current, alpha)`. Плата за плавность — отставание на один тик (50 мс).

**Ввод**
- Нажатия (`WasKeyPressed`) и движение мыши относятся к кадру. В тике их читать нельзя: при FPS выше TPS большинство кадров проходит без тиков, и нажатие потеряется. В тике читается только удержание (`IsKeyDown`).
- Взгляд мышью применяется каждый кадр (мгновенный отклик), движение — в тиках.
- Управление: WASD — ходьба, Space — прыжок (в полёте вверх), Shift — в полёте вниз, Ctrl — бег (быстрый полёт), мышь — взгляд, ЛКМ и ПКМ — основное и дополнительное действие предмета (удержание ПКМ и ЛКМ в творческом повторяет действие раз в 0,2 с; повтор идёт только от нажатия, увиденного в игре, — кнопка, зажатая в инвентаре или кликом захвата курсора, не действует), 1–9 и колесо — слот хотбара, Q — выбросить штуку из руки (Ctrl+Q — всю стопку), Enter или кнопка — возродиться на экране смерти, F — полёт (только в творческом), G — смена режима (временно), E — экран инвентаря (там ЛКМ по рецепту делает одну штуку, Shift+ЛКМ — сколько хватит, колесо над рецептами — прокрутка), J — журнал заданий, Esc — отпустить курсор, клик в окне — захватить.

**Клиент и сервер**
- Клиент и сервер общаются только сообщениями через `IConnection`. Для одиночной игры — `LocalConnection` (две потокобезопасные очереди), для мультиплеера будет сетевая реализация.
- Сообщения — неизменяемые `record`: в памяти они передаются по ссылке.
- Встроенный сервер работает в своём потоке (`ServerHost`) с фиксированным тиком 20 TPS и не зависит от кадров клиента: пока окно тащат мышью, мир живёт. Время тиков отсчитывается от старта, поэтому средняя частота точная; отдельный промежуток между тиками может доходить до ~62 мс из-за точности таймера Windows (15,6 мс). Отставание больше 0,25 с не догоняется.
- Всё состояние `GameServer` принадлежит потоку сервера и меняется только внутри `Tick`. Снаружи можно лишь подключать клиентов (`Connect` кладёт соединение в потокобезопасную очередь, сессия появляется в следующем тике) и обмениваться сообщениями. Новый вход в сервер из чужого потока — только через такую же очередь.
- Если поток сервера упал, исключение сохраняется в `ServerHost.Fault`, а клиент в следующем тике останавливается с этой ошибкой, а не рисует замерший мир.
- Кадры клиента дольше 0,25 с пишутся в лог (`[Engine] Кадр длился …`).
- Сервер принимает только сообщения, разрешённые в текущем состоянии сессии; незнакомое пишется в лог, а не роняет сервер.

**Позиции и точность**
- Абсолютные позиции в мире (игрок, глаз камеры, начало луча, точка появления, позиции в сообщениях) — в `double` (`Shared.Vector3d`). У `float` на миллионе блоков шаг 1/16 блока: движение, выбор блока лучом и будущая физика «ступенили» бы. Направления, смещения, вершины мешей и матрицы — во `float`.
- `Vector3` неявно приводится к `Vector3d` (без потерь). Обратно — только явно (`ToVector3()`) и только для маленьких величин, например смещения от камеры.
- Клиент шлёт `PlayerMove` только после `JoinAccepted`: до него его позиция — начало координат, и сервер начал бы грузить чанки вокруг неё.

**Прочее**
- Консоль выводит UTF-8, чтобы кириллица не ломалась в перенаправленных логах.

## 9. План этапа 1: воксели

**Цель:** летаем над текстурированным ландшафтом примерно 256×256 блоков, ломаем и ставим блоки. FPS не ниже 60 на встроенной видеокарте (Intel UHD 730), автотесты зелёные.

### Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Размер чанка | 32×32×32, кубические чанки | Мир не ограничен по высоте. Чанков в 8 раз меньше, чем при 16³, значит меньше вызовов отрисовки (важно для встроенной видеокарты). Плата: перестроение меша после изменения блока дороже, около 1–3 мс |
| Хранение блоков | плоский массив `ushort[32768]`, индекс `x + z·32 + y·32·32` | Просто и быстро. Сжатие палитрой — позже, когда понадобится память или сеть |
| Идентификатор блока | числовой `BlockId` (`ushort`) в рантайме, строковый `"base:stone"` как постоянное имя | Числовые id раздаются при запуске, поэтому моды не конфликтуют за номера. В сохранениях и сети будет строковое имя или таблица соответствия. Воздух всегда 0 |
| Координаты | блок — `int`; чанк = `coord >> 5`, позиция внутри чанка = `coord & 31` | Деление `/ 32` для отрицательных координат даёт неверный чанк (−1 / 32 = 0, а нужен −1). Классический источник багов, его покрывают тесты |
| Позиции вершин | вершины в локальных координатах чанка, смещение чанка — через матрицу модели | Числа в меше маленькие и точные. Рендер относительно камеры (против дрожания вдали от центра мира) — на этапе 2 |
| Текстуры | массив текстур, 16×16, фильтрация nearest + mip-карты | Нет протекания соседних текстур, позже позволяет greedy meshing. Для начала — сгенерированные заглушки, их можно заменить файлами с теми же именами |
| Освещение | постоянная яркость по направлению грани: верх 1.0, север/юг 0.8, восток/запад 0.6, низ 0.5 | Объём без системы освещения. Настоящий свет и затенение углов (AO) — позже |
| Изменение блоков | только через сервер: клиент шлёт запрос, сервер проверяет и рассылает результат | Сервер — единственный владелец мира. Предсказания на клиенте пока нет: в одиночной игре задержка один тик (50 мс), её не видно |
| Построение мешей | в основном потоке, с замером времени | Сначала правильность, потом скорость. Замер станет точкой отсчёта для фонового построения на этапе 2 |

## 10. План этапа 2: бесконечный мир

**Цель:** летим в любую сторону сколько угодно. Мир подгружается вокруг игрока и выгружается позади без заметных подвисаний (ни один кадр не дольше 20 мс). Не меньше 60 FPS на Intel UHD 730 при дальности 6 чанков. Изменения мира сохраняются и переживают перезапуск.

### Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Где работает сервер | в своём потоке, с собственным циклом фиксированного тика. Клиент и сервер общаются только через очереди (они уже потокобезопасные) | Пока окно тащат мышью, мир продолжает жить. Тяжёлая работа сервера не отнимает время у кадров |
| Генерация чанков | в фоновых потоках сервера. Основной поток сервера только забирает готовые чанки | Генерация чанка — миллисекунды. Сотня чанков при входе подвесила бы тик сервера |
| Шум | FastNoiseLite, сид мира хранится в сохранении | Готовые OpenSimplex2, фракталы, искажение координат. Генерация детерминирована по сиду |
| Высота мира | без предела по Y (кубические чанки). Рельеф генерируется примерно в диапазоне от −64 до +192, ниже — камень, выше — воздух | Бесконечный по высоте мир без особых случаев в коде |
| Какие чанки загружать | сервер ведёт для каждого игрока набор чанков в цилиндре: по горизонтали — дальность прорисовки, по вертикали — ±4. Загружается на кольцо больше: меш строится, только когда у чанка есть все соседи (уточнено на шаге 2.4). Недостающие — от ближних к дальним; ушедшие за радиус с запасом в 2 кольца выгружаются у клиента (`ChunkUnload`) | Запас при выгрузке (гистерезис) нужен, чтобы чанки на границе не загружались и выгружались туда-сюда, когда игрок топчется на месте |
| Дальность прорисовки | 6 чанков (192 блока) по умолчанию, позже — настройка | Рассчитано на встроенную видеокарту. Это как 12 чанков в Minecraft |
| Скорость отправки | не больше 16 чанков клиенту за тик; одновременно генерируется не больше 64 | Иначе при входе клиент получит сотни чанков разом, а очередь генерации будет копить то, что игрок уже пролетел |
| Сжатие чанков | палитра (список разных блоков чанка + индексы наименьшей нужной разрядности) + Deflate. Один формат для сети и сохранений | Чанк 64 КБ превращается в единицы КБ. Нужно и для сети, и для диска |
| Построение мешей | в фоновых потоках, по снимку чанка с рамкой из соседей. Основной поток снимает снимки и загружает готовые меши в видеопамять в пределах бюджета времени на кадр (по 2 мс) | Мир клиента меняется только в основном потоке, поэтому фоновой задаче нужен снимок. Бюджет на кадр — чтобы сотни мешей не дали один длинный кадр |
| Отсечение невидимого | frustum culling: чанк рисуется, только если его куб пересекает пирамиду видимости камеры | Примерно половина чанков всегда позади камеры |
| Рендер относительно камеры | смещение чанка от камеры считается в `double`, в шейдер идёт уже маленькое число. По решению на шаге 2.6 все абсолютные позиции (игрок, протокол, сервер, луч) тоже в `double` | Вдали от центра мира (сотни тысяч блоков) `float` теряет точность: мир дрожит, движение и выбор блока «ступенят» |
| Формат сохранения | SQLite, один файл на мир: таблица `meta` (сид, версия формата, позиция игрока, таблица имён блоков) и таблица `chunks` (позиция → сжатый блок данных) | Атомарные записи: сбой не испортит мир. Так делает Vintage Story |
| Что сохранять | все сгенерированные чанки | Генератор будет меняться по ходу разработки. Если хранить только изменённые, нетронутые места пересоздадутся по-новому, и рядом с постройками появятся обрывы |
| Когда сохранять | при выгрузке чанка, автосохранение раз в минуту, при выходе | Потеря при сбое — не больше минуты игры |
| Id блоков в сохранении | в файле хранится таблица имён блоков; при загрузке числовые id переводятся по именам | Числовые id могут измениться при добавлении блоков и модов, имена — нет |
| Где лежат сохранения | `%LOCALAPPDATA%\<название игры>\Saves\` (Linux: `~/.local/share/<название игры>/Saves/`) | Не в папке сборки: её удаляет `dotnet clean`. Название берётся из `GameName` |

### Открытые вопросы этапа 2

- Распаковка пришедших чанков идёт в основном потоке, в тике клиента: кадр входа в мир ~16 мс. Вынести в фон можно, но нужно сохранить порядок с `BlockChanged` и `ChunkUnload`.
- Изредка (не воспроизвелось в повторах) кадр входа длится 23–29 мс в Debug вдали от центра. Причина не найдена.
- При полёте высоко видно только на 4 чанка вниз: дно низин ниже уровня моря не рисуется, сквозь него видно небо. У земли этого нет; решать вместе с физикой игрока или дальностью, зависящей от высоты.
- Промежуток между тиками сервера доходит до ~62 мс из-за таймера Windows (15,6 мс); средняя частота точная. Если начнёт мешать — `timeBeginPeriod(1)`.
- С сохранениями средний тик сервера в Debug вырос с ~2 до 3–4,6 мс, хотя запись идёт не в тике. Видимо, потоки сохранения и сжатия отнимают процессор у потока сервера; отдельно не замерено. Запас до 50 мс большой.
- Если поток сервера не остановился за 5 с (`ServerHost.Stop`), `GameServer.Dispose` всё равно сохраняет мир — одновременно с тиком. Так было и раньше, но теперь от этого зависит сохранение.
- ~~Не сохраняются направление взгляда и выбранный слот хотбара.~~ Решено на шаге 3.5 (схема сохранения 2).
- Сохранение растёт без предела: в него попадает каждый сгенерированный чанк, в том числе пустой воздух над рельефом (~8 байт данных плюс накладные расходы SQLite).

### Не входит в этап 2

Вода и другие жидкости, пещеры, полноценные биомы, деревья и постройки при генерации, освещение и затенение углов, уровни детализации для дальних чанков, физика игрока, настоящий сетевой транспорт, меню выбора мира. Всё это — следующие этапы.

## 11. План этапа 3: игрок

**Цель:** вместо летающей камеры — игрок с телом: ходит, прыгает, падает, упирается в стены. Сломанный блок попадает в инвентарь, поставленный тратится (режим выживания); в творческом режиме блоки бесконечные и можно летать. Хотбар и экран инвентаря нарисованы на экране, предметы перетаскиваются мышью. Инвентарь и режим переживают перезапуск. Производительность — не хуже замеров этапа 2: ни одного кадра дольше 20 мс.

### Решения

Развилки «кто считает движение», «какой интерфейс», «какие режимы», «куда попадает добыча» решены пользователем (2026-10-13); остальное — предложения плана.

| Вопрос | Решение | Почему |
|---|---|---|
| Кто считает движение | **клиент**, кодом физики из Shared. Сервер тем же кодом проверяет правдоподобие: тело не внутри блоков, скорость не больше возможной для режима. Нарушение — сервер возвращает игрока на последнюю верную позицию (`PlayerTeleport`) | Движение без задержки и без сложной схемы «предсказание + сверка». Общий код коллизий — один источник правды. В мультиплеере защищает от простых читов (сквозь стены, телепорт, сверхскорость). Полный серверный расчёт с предсказанием можно сделать позже, физика к этому готова: она чистая функция «состояние + ввод → состояние» |
| Тело игрока | прямоугольный короб (AABB) 0,6 × 1,8 × 0,6, глаз на высоте 1,62 от ног. Позиция игрока — **точка ног** (центр нижней грани), а не глаз | Размеры как в Minecraft: игрок проходит в проём 1 × 2 и не проходит в 1 × 1. От ног проще считать опору и прыжок. Меняется смысл позиции в `PlayerMove` и в сохранении |
| Столкновения | короб против полных кубов. Перемещение за тик раскладывается по осям: сначала Y, затем X и Z; по каждой оси движение обрезается о ближайший блок на пути. Проверяются все блоки в коробе «тело + весь путь за тик», поэтому на любой скорости тело не проскакивает сквозь стену. Координаты — `double` | Классическая и надёжная схема (Minecraft, большинство воксельных игр). Раздельные оси дают скольжение вдоль стен. `double` — по правилу раздела 8: на миллионе блоков `float` дал бы ступеньки |
| Какие блоки твёрдые | новое свойство блока `IsSolid` в реестре (рядом с `IsOpaque`). Пока все блоки, кроме воздуха, твёрдые и полные | Непрозрачность и твёрдость — разные свойства: стекло прозрачное, но твёрдое, а высокая трава прозрачная и проходимая, по одной прозрачности их не различить. На этапе 4 свойство придёт из JSON, позже — короба нестандартной формы (плиты, ступени) |
| Незагруженные чанки | если тело касается незагруженного чанка, игрок стоит на месте (гравитация не действует) | Иначе при входе или быстром полёте игрок провалился бы сквозь ещё не пришедший мир |
| Числа физики | 20 тиков в секунду, как сейчас. Ходьба ~4,3 блока/с, бег (Ctrl) ~5,6, гравитация 32 блока/с², прыжок на ~1,25 блока, предельная скорость падения ~78 блоков/с, полёт ~11 (с Ctrl ~22). Подбираются вживую | Близко к Minecraft: привычное ощущение и проверенные пропорции (прыжок на один блок, но не на два) |
| Режимы игры | **выживание и творческий**, режим — свойство игрока, хранится в сохранении. Новый игрок получает режим мира по умолчанию: аргумент `--mode survival\|creative` при создании мира (по умолчанию выживание). Переключение — клавишей G (временно, до команд и прав доступа): клиент шлёт `SetGameMode`, сервер в одиночной игре разрешает | Выбор пользователя «оба режима». Творческий нужен и для проверок: полёт к дальним точкам, любые блоки без добычи |
| Полёт | только в творческом режиме, переключается клавишей F. Полёт **со столкновениями**. Свободный полёт сквозь блоки убираем | Сервер проверяет движение одинаково во всех режимах, отличаются только пределы скорости. Скрипты проверок летают выше рельефа, как и сейчас |
| Предметы | `ItemId` и `ItemRegistry` в Shared, отдельно от блоков. Каждый блок регистрирует одноимённый предмет (`base:stone`), который его ставит. Стопка `ItemStack(ItemId, Count)`, предел стопки — свойство предмета (64 для блоков) | Предмет и блок — разные сущности: инструменты, еда, оружие не ставятся в мир. До шага 3.4 `Hotbar` хранил `BlockId` — это была временная заглушка этапа 1. На этапе 4 предметы будут описаны в JSON |
| Инвентарь | 36 слотов: 9 хотбара (клавиши 1–9 и колесо мыши) и 27 основных. Авторитетная копия на сервере; клиент шлёт намерения (`InventoryClick`: слот и кнопка), сервер применяет их общим кодом из Shared и присылает изменённые слоты. «Предмет на курсоре» (взятый мышью) тоже живёт на сервере | Хотбар расширяется с 6 до 9 — привычная раскладка. Сервер не верит клиенту и в инвентаре: клиент не может «нарисовать» себе предметы. Задержка в одиночной игре — один тик, её не видно, поэтому без предсказания на клиенте |
| Добыча и трата | *(заменено на шаге 7.3: добыча падает предметом и подбирается, блок ломается и при полном инвентаре)* выживание: сломанный блок сразу кладётся в инвентарь (в подходящую стопку, иначе в первый пустой слот, сначала хотбар). **Если положить некуда, блок не ломается.** Поставленный блок отнимает одну штуку. Творческий: ломание ничего не даёт, установка ничего не тратит | Выбор пользователя «сразу в инвентарь». Предметов на земле нет до системы сущностей (этап 4); не ломать при полном инвентаре — чтобы ничего не терялось молча |
| Стартовый инвентарь | выживание — пустой; творческий — экран инвентаря показывает палитру всех предметов, из неё берутся стопки | Брёвен и досок в выживании пока не добыть (деревьев нет) — для них есть творческий режим |
| Установка блока | сервер не ставит блок, если он пересекает тело любого игрока | Заменяет временную проверку «не в глаз камеры» из этапа 1 |
| 2D-интерфейс | свой, в `Engine.Ui`: `SpriteBatch` (прямоугольники с текстурой и цветом, все в один вызов отрисовки на текстуру, ортографическая проекция в пикселях) и растровый шрифт. Масштаб интерфейса — целый (1×, 2×, 3×) по высоте окна, чтобы пиксели не размывались. На шаге 3.6 вышло лучше плана: один вызов на весь интерфейс с двумя текстурами сразу (раздел 8, «Интерфейс») | Выбор пользователя. Станет основой всего будущего интерфейса (меню, сундуки, крафт). Свой, а не ImGui: игровой вид и полный контроль |
| Шрифт | TTF с кириллицей под свободной лицензией (OFL) в `Assets/Fonts`, растеризуется при запуске в атлас (StbTrueTypeSharp — от того же автора, что StbImageSharp). Выбран пользователем на шаге 3.6 по скриншотам из четырёх (Pixelify Sans, Press Start 2P, PT Sans, Golos Text): **Press Start 2P** — пиксельный | Кириллица обязательна. Растеризация при запуске — любой размер без отдельных утилит |
| Иконки блоков | рисуются прямо в интерфейсе как изометрический кубик: три четырёхугольника (верх, левый и правый бок) с текстурами из уже загруженного массива текстур и яркостью по грани, как в мире | Без отдельного рендера в текстуру и без новых файлов. Новый блок автоматически получает иконку |
| Сохранение игрока | схема сохранения версии 2: к игроку добавляются режим, инвентарь (двоичный блок с версией, предметы — в номерах сохранения через таблицу `item_names`, как блоки), выбранный слот, направление взгляда. Сохранение версии 1 обновляется при открытии (`ALTER TABLE`) | Закрывает открытый вопрос этапа 2 (взгляд и слот). Перевод id предметов по именам — по тому же правилу, что для блоков: числовые id могут поменяться, имена нет |

### Открытые вопросы этапа 3

- Обработка `PlayerTeleport` на клиенте вживую не проверена: честный клиент поправок не получает, а вызвать телепорт из игры пока нечем. Сервер покрыт тестами (`MovementTests`). Проверить, когда появится команда телепорта или временной поломкой клиента.
- Возможны редкие ложные поправки движения: другой игрок ставит блок туда, куда вы шагнули в тот же тик (сервер проверяет тело по позиции на тик раньше). В одиночной игре не бывает.
- Отклонения движения пишутся в лог без ограничения частоты: нечестный клиент в мультиплеере засыпал бы лог. Ограничить вместе с сетью.
- Ощущение движения (скорости, прыжок, инерция в воздухе) взято по образцу Minecraft и пользователем пока принято «как есть»; подстроить, если будет неудобно.
- Этап 3.7 завершён и проверен: сборка, автоматические тесты и ручной playtest пользователя.
- Перетаскивание не включает слот, с которого началось (в Minecraft включает), а «взял стопку и повёл» сразу распределяет её по слотам (в Minecraft — ничего). Решить, оставляем ли так.
- Разметка экрана инвентаря считается в трёх местах (`Draw`, `HitSlot`, `FindHovered`), и тестов у `InventoryScreen` нет; расхождение уже было (палитра). Вынести в отдельный класс раскладки, как `HudLayout`, и покрыть тестами.
- Высота панели в творческом режиме рассчитана на 3 ряда палитры (27 предметов). С контентом этапа 4 палитра перестанет помещаться: нужна прокрутка или страницы.
- `InventoryScreen` каждый кадр строит список предметов палитры (`Where(...).ToArray()`) и грузит свой экземпляр шрифта и атласа отдельно от `Hud`. Реестр после запуска не меняется — список можно посчитать один раз, атлас — общий.
- Сервер не удаляет сессии отключившихся клиентов (`GameServer._sessions`). В одиночной игре не важно; сделать вместе с сетью.
- У Press Start 2P шаг строк равен высоте глифа (подъём 8 клеток, спуска и промежутка нет): строки текста касаются друг друга. Подсказки текущего экрана однострочные; если появятся многострочные, добавить межстрочный промежуток в раскладке.
- Кернинг тестами не проверен: в Press Start 2P его нет, и поломка кернинга ничего не меняет. Проверить, если появится шрифт с кернингом.
- Вход в мир по-прежнему даёт кадры около 20 мс (19,8–21,4 мс в Release) — их дают меши первых чанков; интерфейс добавляет к кадру около 0,6 мс.
- В творческом режиме до шага 3.7 (палитра) взять блоки неоткуда: новый игрок начинает с пустым инвентарём. Пока блоки можно набрать в выживании и переключиться клавишей G — инвентарь при смене режима сохраняется.
- Гравитацию сервер не проверяет: нечестный клиент в выживании может висеть в воздухе и подниматься со скоростью прыжка. Для одиночной игры не важно; проверить вместе с сетью.

### Не входит в этап 3

Здоровье, урон от падения, голод, смерть и возрождение. Предметы на земле и выбрасывание (Q) — с сущностями на этапе 4. Время ломания блока и инструменты (ломание остаётся мгновенным). Крафт, сундуки. Приседание и защита от падения с края, плавание (воды нет), лестницы, автоподъём на ступеньку. Вид от третьего лица и модель игрока. Отображение других игроков. Полностью серверное движение с предсказанием. Чат, команды и права доступа (переключение режима G — временное). Меню и настройки.

## 12. План этапа 4: система контента

**Цель:** блоки и предметы описываются данными, а не разрозненными условиями в коде. Реестр обеспечивает стабильные строковые идентификаторы с пространством имён, проверку ссылок и единый путь загрузки ванильного и будущего модового контента. Это фундамент для моддинга, но не повод преждевременно внедрять полноценную ECS.

### Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Идентификаторы контента | Строковые ID с пространством имён: например, `base:stone`, `base:stick`, а в будущем `example_mod:amethyst_ore`. Числовые ID, если они нужны для быстрых внутренних операций, назначаются реестром при загрузке и не считаются постоянными | Ванильное пространство имён — `base` (как уже существующий `base:air`), а не название игры: название временное и в коде не пишется. Пространства имён предотвращают конфликты ванильного контента и модов. Строковые ID можно безопасно хранить в сохранениях и сопоставлять после изменения порядка загрузки |
| ECS | Внедрять постепенно, когда появятся конкретные механики и требования к компонентам. На этом этапе проектируем реестр и определения контента; не переносим блоки, предметы и игрока на полноценную ECS без практической необходимости | Не создавать архитектуру заранее без проверяемого сценария. Data-driven определения и ECS — совместимые, но разные задачи |
| Формат описаний | JSON с валидацией при загрузке. Ошибки должны указывать файл, идентификатор и поле, если их можно определить | Ошибка контента обнаруживается при запуске, а не позже при добыче блока, отрисовке или загрузке мира |
| Ванильный контент | Ванильные определения загружаются тем же механизмом и проходят те же проверки, что и сторонние пакеты контента. Внешняя загрузка C# DLL относится к этапу 5 | Не должно быть отдельного привилегированного пути для встроенного контента |
| Сохранения | Стабильный строковый ID — долговременная идентичность. Существующая схема перевода числовых ID по таблице имён должна оставаться совместимой; миграция проводится отдельно и только при необходимости | Не ломать существующие миры и не делать числовые ID из памяти частью формата контента |

### Шаги

Каждый шаг заканчивается рабочей сборкой, тестами и проверкой в игре. Коммит шага — после проверки и одобрения пользователя.

| # | Шаг | Что делаем | Как проверяем |
|---|---|---|---|
| 4.1 | Реестр и загрузка JSON ✅ | Изучить текущие `BlockId`, `ItemId`, `BlockRegistry`, `ItemRegistry` и потребителей; определить минимальные определения блока/предмета, загрузчик JSON, namespaces и валидацию. Начать с тестируемого Shared-кода, не затрагивая рендер без необходимости | Тесты валидных определений, повторяющихся ID, неверного namespace, отсутствующих/неверных обязательных полей и понятных сообщений об ошибках; сборка и полный набор тестов |
| 4.2 | Ванильные блоки и предметы из данных ✅ | JSON-файлы `content/base/blocks` и `content/base/items` вместо `BaseBlocks`, `BlockVisuals.BaseAppearances` и `ItemRegistry.RegisterBlockItems`; поле `textures` у блока; `GameContent.Load()` на сервере и клиенте; `BaseBlocks` находит блоки по имени. Предметы перенесены в этом же шаге (план отводил им 4.3): загрузчик строит и замораживает оба реестра сразу, дорегистрировать предметы кодом после него нельзя | `GameContentTests` сверяет блоки, свойства, текстуры и предметы с прежними таблицами кода; тесты поля `textures` и загрузки каталога; проверка поломкой (неверная текстура, опечатка в имени файла, путь вместо имени текстуры, перепутанный блок в `BaseBlocks`) — падают нужные тесты. Вживую под Linux: мир, созданный прошлой версией (блок поставлен, хотбар заполнен), открыт новой — блоки и инвентарь на месте, предупреждений о неизвестных именах нет; в новом мире генерация, текстуры, ломание и установка в выживании. 473/473 тестов |
| 4.3 | Ванильные предметы из данных — объединён с 4.2 | — | — |
| 4.4 | Целостность контента и обратная совместимость ✅ | Пакет = папка верхнего уровня = пространство имён: определения пакета — только `<пакет>:…`, JSON вне папки пакета и неверное имя пакета — ошибка. `ContentLoader.LoadDirectories` грузит пакеты из нескольких корней (для модов этапа 5), один пакет в двух корнях — ошибка. Ошибка контента при запуске — одна строка `[Content] …` с файлом и код выхода 1. Ссылки блок ↔ предмет проверял загрузчик с 4.1, файлы текстур — тест с 4.2; неизвестные имена в сохранениях и другой порядок id покрыты тестами этапа 2–3 | Негативные тесты пакетов и корней; тест «сохранение с порядком id из кода (до 4.2) открывается с реестрами из контента»; проверка поломкой — проверки пространства имён, двух корней, файла вне пакета и перевода id при чтении чанка ловят нужные тесты. Вживую: испорченный JSON в сборке — сообщение и выход; мир прошлой версии открыт новой без потерь. Производительность (Linux, Iris Xe, Release, вход + полёт, по 3 прогона): до этапа 4 и после — одинаково в пределах шума (см. открытые вопросы). 482/482 тестов |

### Открытые вопросы этапа 4

- Порядок в творческой палитре теперь — порядок id, то есть алфавит имён (dirt, grass, log, planks, sand, stone); раньше был порядком регистрации в коде (камень первым). Если нужен «осмысленный» порядок — отдельное поле или вкладки палитры.
- Под Linux (Iris Xe, niri, 60 Гц) вход в мир даёт кадры 28–78 мс в Release, в полёте — до 20–25 мс и 0–3 кадра дольше 20 мс за 10 с; так и до этапа 4, и после (замеры шага 4.4). Под Windows на UHD 730 было 15–19 мс без кадров дольше 20 мс (этап 2). Причина не искалась: разделить кадр на части (CPU, `glFinish`) под Linux, сравнить с Windows.
- Время загрузки контента не замерялось: 12 маленьких файлов при запуске, в кадре и тике контент не участвует. Замерить, когда файлов станет много.

### Не входит в этап 4

Загрузка внешних C# DLL и публичный API модов (этап 5); полноценная ECS без конкретного сценария; новые игровые механики и компоненты вроде еды, горения, инструментов и роста; крафт, сущности и предметы на земле; редактор контента; горячая перезагрузка JSON; произвольные формы блоков и изменение формата чанков без необходимости.

### Критерии завершения этапа

- Все существующие ванильные блоки и предметы загружаются через единый data-driven путь.
- Идентификаторы имеют пространство имён и не зависят от порядка регистрации.
- Ошибочный контент отклоняется при загрузке с полезным сообщением; критические проверки покрыты тестами, которые действительно падают при внесении соответствующей ошибки.
- Существующие миры загружаются без потери блоков и предметов.
- Сборка без ошибок и предупреждений, все автоматические тесты проходят; проверены запуск мира, генерация, отрисовка, ломание/установка и инвентарь.
- Нет регрессии производительности, выходящей за разумные колебания замеров этапа 2.

## 13. План этапа 5: API модов

**Цель:** сторонний мод, положенный в папку модов, добавляет блоки и предметы со своими текстурами и названиями, задаёт предметам поведение на C# и реагирует на события мира — без изменения кода игры. Ванильное поведение подключено через тот же публичный API. Мод может явно заменить чужое определение. Пример мода лежит в репозитории и проверяется тестами и вживую.

### Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Где лежат моды | Общая папка: `%LOCALAPPDATA%\<название игры>\Mods\<мод>\` (Linux: `~/.local/share/<название игры>/Mods/<мод>/`); моды включены во всех мирах. Аргумент `--mods ПАПКА` подменяет папку (проверки вживую не трогают моды пользователя). Мир запоминает, с какими модами (id и версия) его открывали, и при открытии пишет в лог, каких не хватает | Выбор пользователя. Проще всего для начала (как tModLoader); список модов на мир требует меню выбора, которого нет |
| Устройство мода | Папка с `mod.json` (`id`, `name`, `version`, `dependencies`, необязательный `assembly`), `content/` (JSON, как у пакета) и `textures/blocks/*.png`. **Id мода = пакет = пространство имён** его определений — правило этапа 4 не меняется | Один идентификатор на всё: по имени `example_mod:wand` сразу видно мод, папку и сборку |
| Порядок загрузки | По зависимостям (`dependencies`: id → минимальная версия), при равенстве — по id. Нет зависимости, цикл, несовместимая версия — ошибка запуска с понятным сообщением, как у ошибок контента | Порядок важен для замены определений и регистрации поведений; он должен быть предсказуемым и не зависеть от файловой системы |
| Код модов | C#-сборка (DLL), полное доверие (как tModLoader, SMAPI, Vintage Story): каждая — в своём `AssemblyLoadContext`, общие сборки (API, Shared) берутся из игры, чтобы типы совпадали. Точка входа — класс с интерфейсом `IMod`, метод `Load(IModContext)`. Выгрузки и горячей перезагрузки нет | Решение 4 раздела 4. Свой контекст загрузки — чтобы зависимости разных модов (разные версии одной библиотеки) не конфликтовали |
| Публичный API | Новый проект `src/Api` (сборка `<название игры>.Api`, зависит от Shared): `IMod`, `IModContext`, `IItemBehavior` и контекст применения, `IWorld`/`IPlayer` — узкие публичные обёртки над внутренностями сервера, события. Server ссылается на Api и реализует его; внутренние типы сервера остаются `internal` | Мод зависит от маленькой стабильной сборки, а не от всего сервера: внутренности можно менять, не ломая моды (как VintagestoryAPI.dll) |
| Поведение предметов | Предмет в JSON ссылается на поведение по id: `"behavior": "example_mod:wand"`. По умолчанию — `base:place_block` у предмета с `placesBlock`, иначе `base:hand`. Поведения регистрирует код модов (`context.RegisterItemBehavior(id, behavior)`); ссылка на незарегистрированное поведение — ошибка запуска. Поведение исполняется только на сервере | Data-driven: связь «предмет → поведение» — в данных, код только реализует поведение. Заменяет зашитую таблицу `ItemBehaviors` |
| Ваниль | Встроенный мод `base` внутри игры (не DLL): ванильные поведения (`base:hand`, `base:place_block`) и обработчики регистрируются через тот же `IModContext`, что и у сторонних модов | Принцип «ванилла — это тоже мод» (выбор пользователя): пробел в API виден сразу на самой игре |
| События мира | `BlockBroken` (игрок, позиция, блок), `BlockPlaced` (игрок, позиция, блок), `PlayerJoined` (игрок) — уже случившиеся, без отмены. Вызываются в потоке сервера в конце действия. Исключение в обработчике мода пишется в лог с id мода и не роняет сервер | Выбор пользователя: реакция на мир без правки кода игры. Отмена (защита территорий) требует продуманного порядка обработчиков — позже |
| Замена определений | Файл мода с `"override": true` целиком заменяет определение с тем же именем из другого пакета; без флага чужое пространство имён — по-прежнему ошибка. Заменять можно только определения пакетов, от которых мод зависит (порядок становится явным); два мода, заменяющих одно имя без зависимости между собой, — ошибка. Имя не меняется, поэтому сохранения не затрагиваются; стопки в сохранении больше нового предела стопки при загрузке урезаются (с записью в лог) | Выбор пользователя: явная замена. Требование зависимости убирает неоднозначность «кто последний»; урезание стопок не даёт упасть на `Inventory.Set` |
| Текстуры и названия | Имя текстуры в JSON без пространства имён ищется в своём пакете (`stone` у `base` → `Assets/Textures/Blocks/stone.png`, у мода → `Mods/<мод>/textures/blocks/…`), с пространством имён (`base:stone`) — в указанном. Название предмета для игрока — поле `displayName` в JSON предмета; ванильные названия переезжают из `ItemNames` в контент | Без этого блок мода был бы шахматкой без имени. Переводы — позже, `displayName` — одна строка на предмет |

### Шаги

Каждый шаг заканчивается рабочей сборкой, тестами (с проверкой поломкой), проверкой в игре и отчётом; коммит — после одобрения пользователя.

| # | Шаг | Что делаем | Как проверяем |
|---|---|---|---|
| 5.1 | Публичный API и ванильный встроенный мод ✅ | Проект `src/Api`: `IMod`, `IModContext`, публичные `IItemBehavior` и контекст применения, `IWorld`/`IPlayer`. Поле `behavior` в JSON предмета, реестр поведений по id вместо `ItemBehaviors`. Ванильные поведения регистрирует встроенный мод `base` через API. Внешних модов ещё нет | Тесты реестра поведений (по умолчанию, явное, неизвестное — ошибка); все тесты действий предметов без изменений; вживую — ломание и установка как раньше |
| 5.2 | События мира ✅ | `IModEvents` (`OnBlockBroken`, `OnBlockPlaced`, `OnPlayerJoined`) в `IModContext`. Уточнение плана: события поднимает не код ванильных поведений, а мир — новые `IWorld.TryBreakBlock` / `TryPlaceBlock` с игроком; так их порождает и поведение любого мода. Очередь событий разбирается после каждого сообщения, лимит цепочки, изоляция исключений | Тесты на настоящем сервере с тестовыми модами (`ModEventsTests`): событие одно и приходит, когда добыча уже в инвентаре; при отказе (полный инвентарь, пустая рука) событий нет; изменения инвентаря из `PlayerJoined` доходят до клиента; исключение одного мода не мешает другому и пишется в лог с id; бесконечная цепочка обрывается; подписка после загрузки — ошибка. Проверка поломкой (нет разбора очереди, вызов сразу, нет изоляции, нет заморозки, нет `PlayerJoined`) — падают нужные тесты. ### Открытые вопросы этапа 5

- ~~`ChunkGeneratorTests.Dispose_DropsQueuedRequests_AndReturnsQuickly` падал при полном прогоне~~ — решено перед шагом 6.2: тест проверял «очередь отброшена» через «Dispose быстрее 500 мс», а Dispose честно ждёт чанк в работе (первый — с JIT-компиляцией шума, под нагрузкой сотни мс). Теперь без часов: первый чанк придерживается, пока Dispose не очистит очередь, и проверяется, что сделан ровно один чанк (`…_FinishesOnlyChunkInProgress`).
- ~~`ServerHostTests.TickRate_MatchesTicksPerSecond` изредка падал~~ — решено перед шагом 6.2. Причина — устройство `ServerHost`, а не случайность: под нагрузкой отставание больше `MaxLagSeconds` пропускается без тиков, а меньшее догоняется позже, и в момент чтения тиков законно не хватает. Сервер теперь считает пропущенное время (`SkippedSeconds`), тест сравнивает с ним, а нижняя граница выведена из `MaxLagSeconds` (−(0,25 × 20 + 1)); новый тест `LongTick_IsSkippedNotCaughtUp_AndCounted` проверяет сам пропуск. 8 полных прогонов под нагрузкой на все ядра — без падений (до исправления — 2 из 5). Остался один тест со временем — `Stop_WakesThreadImmediately` (остановка быстрее 500 мс при ожидании в 1 с): запас вдвое, под нагрузкой не падал; полностью без часов — только с подменой времени в `ServerHost`.

- ~~Предметы, которые не блоки, рисуются квадратом «нет текстуры»~~ — решено на шаге 6.1 (поле `icon`).

### Не входит в этап 5

Клиентский API (свои экраны, отрисовка, ввод); отменяемые события и тик сервера для модов; выгрузка и горячая перезагрузка модов; песочница и ограничение прав кода модов; частичные правки чужих определений; список модов на мир и меню модов; загрузка модов из сети и синхронизация модов в мультиплеере (кроме уже существующей сверки таблиц имён); ECS-компоненты; переводы.

### Критерии завершения этапа

- Пример мода из папки модов добавляет блок и предмет со своими текстурой и названием, поведение палочки и обработчик события работают — без изменения кода игры.
- Ванильное поведение подключено через тот же публичный API; мод зависит только от сборок Api и Shared.
- Ошибки модов (манифест, зависимости, контент, сборка, исключение в обработчике) дают понятное сообщение с id мода; ошибка обработчика не роняет сервер.
- Замена определения работает только явно и предсказуемо; существующие миры открываются без потерь.
- Сборка без ошибок и предупреждений, все тесты зелёные; руководство позволяет сделать мод с нуля; нет регрессии производительности.

## 14. План этапа 6: первая геймплейная петля

**Цель:** новый игрок в выживании проходит путь от голых рук до медной кирки: рубит дерево, делает верстак и деревянную кирку, добывает камень, делает каменные инструменты и печь, находит медную руду, плавит медь и делает медную кирку. Ломание занимает время и зависит от инструмента, предметы делаются по рецептам у станков, задания подсказывают следующий шаг и отмечают достижения. Всё новое описано данными и доступно модам.

### Решения

| Вопрос | Решение | Почему |

| Ядро | Добыча → ремесло → стройка, лестница инструментов дерево → камень → медь | Выбор пользователя. Почти целиком на существующих системах (мир, предметы, инвентарь, моды); нужно любому следующему ядру (ферме, выживанию с угрозой) |

### Открытые вопросы этапа 6

- Листва даёт саму себя, а не «иногда палку», как записано в решениях: таблиц добычи (вероятности, несколько предметов) пока нет. Палки — рецептом из досок (сделано на шаге 6.4); таблицы добычи — отдельной задачей.
- Список рецептов перестраивается после каждого крафта (доступные сверху), и под мышью может оказаться другой рецепт: второй клик подряд сделает не то же самое (так же в Terraria). Если будет мешать — держать порядок, пока экран открыт.
- Творческая палитра растёт с числом предметов: больше трёх строк (27 предметов) не помещаются в 320 × 240. С модами нужна прокрутка палитры, как у рецептов.
- Рецепт в `CraftRecipe` передаётся именем, а не числом: проще и не требует сверки таблиц; для сети, если окажется дорого, — номер с таблицей в `JoinAccepted`, как у блоков.
- Подсказка заданий в углу и уведомление справа на экране 320 × 240 при длинных названиях могут сойтись: ширина подсказки не ограничена. Если будут длинные названия у модов — обрезать подсказку.
- Награды за задания — только кодом мода (`OnQuestCompleted`); данными (`reward` в JSON) — когда понадобится.
- Задание «иметь» засчитывается и предметами, взятыми в творческом, если потом перейти в выживание (проверка идёт по инвентарю). Пока режим меняет кто угодно (G), это неважно; с правами доступа — решить.
- На шаге 6.5 один раз не показалось второе уведомление из очереди («Верстак» после «Доски»); после выноса очереди в `ToastQueue` (логика та же) и повторов вживую не воспроизвелось, тесты очереди зелёные. Причина не найдена — возможно, неточность в оценке времени между кадрами проверки.
- Клиент распаковывает чанки в основном потоке (`ChunkData.ToChunk` в `ProcessServerMessages`): с этапа 6 это ~0,16 мс на чанк, до 16 чанков за тик — ~2,6 мс на входе. Если вход станет заметно дёрганым — распаковывать в фоне (как меши).
- Удержание ЛКМ переходит к следующему блоку на линии взгляда и может сломать только что поставленный станок (при прохождении так ушёл верстак — в инвентарь, не потерялся). Как в Minecraft; если будет мешать — не переходить на блок другого вида, пока кнопку не отпустили.
- Подсказка заданий собирает строки каждый кадр (~544 байт мусора за кадр, 0,05 мс). Если понадобится — пересобирать только при изменении книги или инвентаря.
- ~~Тест `ServerHostTests.LongTick_IsSkippedNotCaughtUp_AndCounted` (до этапа 6) упал один раз из четырёх полных прогонов на шаге 6.4: число тиков сверяется с подобранным допуском по реальному времени.~~ Решено на шаге 8.2 (см. открытые вопросы этапа 8).
- У предмета со своим поведением, который ломает через `Breaker`, клиент не рисует трещины (не знает, что ЛКМ у него — ломание). Если моды начнут так делать — признак в определении предмета.
- Клиент считает время трещин сам; сервер ломает по своим тикам. При заметной задержке связи трещины и момент ломания разойдутся — для одиночной игры не важно, для сети — сообщение о прогрессе от сервера.

### Не входит в этап 6

Мобы и сущности, здоровье, голод и бой; выпавшие предметы на земле; время суток; ферма и рост растений; полупрозрачные блоки и листва с альфой; блоки с состоянием (печь с топливом и временем плавки, сундуки); прочность инструментов; железо и дальнейшие уровни; звук.

### Критерии завершения этапа

- С пустого выживания можно дойти до медной кирки, пользуясь только тем, что даёт мир, рецептами и подсказками заданий.
- Ломание зависит от твёрдости и инструмента, прогресс считает сервер; в творческом — мгновенно.
- Рецепты, инструменты, задания и иконки — данные; моды добавляют свои тем же путём, руководство обновлено.
- Существующие миры открываются (новые блоки появляются только в новых чанках).
- Сборка без ошибок и предупреждений, все тесты зелёные; нет регрессии производительности.

## 15. План этапа 7: сущности, предметы на земле и здоровье

**Цель:** в мире появляется то, что движется и не является блоком. Добыча со сломанного блока падает предметом, притягивается к игроку и подбирается; предметы можно выбросить, они лежат, сливаются и со временем исчезают, переживают перезапуск. У игрока есть здоровье: падение с высоты ранит, при смерти вещи выпадают на месте, игрок появляется в точке появления. Под это — своё небольшое ядро ECS, на котором потом вырастут мобы, животные, снаряды и бой.

### Решения

| Вопрос | Решение | Почему |
|---|---|---|
| ECS | Своя небольшая: сущность — номер с поколением (`EntityId`: индекс + поколение, чтобы старый номер не указал на новую сущность), компоненты — плотные массивы с разреженным индексом (`ComponentStore<T>`, sparse set), запросы по нескольким компонентам, удаление — отложенное, в конце тика. Системы — обычные классы сервера, вызываются в тике в заданном порядке | Выбор пользователя. Сотни–тысячи сущностей ей по силам; типы наши — их можно открыть модам в Api без чужой зависимости. Arch — если упрёмся в скорость (замеры) |
| Где живут сущности | Только на сервере, авторитетно. Клиенту уходят снимки для отображения (вид, позиция, что рисовать), а не компоненты | Как с миром и инвентарём: клиент не решает, только показывает. Под мультиплеер транспорт уже есть |
| Игрок | Становится сущностью: позиция и здоровье — компоненты; `ClientSession` хранит номер сущности, движение по-прежнему через `PlayerMove` и `MovementCheck` | Урон, смерть и (позже) мобы работают с игроком теми же системами, что с любой сущностью, без второго пути в коде |
| Физика | Общий шаг «короб против блоков» выделяется из `PlayerPhysics` (гравитация, обрезка по осям, незагруженный чанк — стоп); у предмета свои параметры (короб 0,25, трение, прыжок при разлёте). Детерминированно, по тикам сервера | Один код столкновений для всех: игрок и предмет не проваливаются по-разному |
| Синхронизация | `EntitySpawned` (номер, вид, позиция, данные вида — например стопка), `EntitiesMoved` — одним сообщением за тик, только изменившиеся, `EntityRemoved`. Получают игроки, у которых есть чанк сущности (как `BlockChanged`); при отправке чанка — его сущности, при выгрузке — удаление у клиента. Клиент интерполирует между тиками, как камеру | Лишнего по сети не шлём; плавность — тем же приёмом, что у игрока |
| Добыча | Сломанный блок всегда ломается и роняет добычу предметом в центре блока с небольшим разлётом (правило «полный инвентарь — блок не ломается» уходит). В творческом добыча не падает (предметы бесконечные) | Выбор пользователя: как в Minecraft и Terraria, добычу видно в мире |
| Подбор | Предмет притягивается к игроку в выживании с 3 блоков и подбирается при касании тела, если в инвентаре есть место (доливается в стопки, остаток остаётся лежать). Задержка подбора: выпавший при ломании — 0,5 с, выброшенный — 2 с (иначе сразу подберётся обратно) | Привычно по обеим играм-ориентирам; задержка — чтобы предмет было видно |
| Выбросить | Q — одну штуку из руки, Ctrl+Q — всю стопку; предмет на курсоре при закрытии инвентаря, если не влез, — тоже выбрасывается (сейчас он остаётся на курсоре невидимым) | Без этого предметы с земли нельзя было бы проверить и ими нельзя было бы делиться |
| Жизнь предмета | Одинаковые предметы в радиусе 0,5 блока сливаются до предела стопки; лежащий предмет исчезает через 5 минут | Тысячи предметов от добычи не копятся бесконечно и не грузят сеть |
| Отрисовка | Предмет-блок — уменьшенный кубик его текстур (медленно вращается), предмет с картинкой — плоская картинка, повёрнутая к камере по горизонтали (вращение плоской картинки показывало бы её ребром); оба покачиваются (уточнено на шаге 7.2). Все предметы кадра — одним вызовом отрисовки (данные экземпляров в буфере) | Тысяча предметов не должна стоить тысячу вызовов отрисовки (урок `glDrawElements` этапа 1) |
| Сохранение | Сущности чанка (кроме игроков) хранятся вместе с чанком: таблица `entities` (позиция чанка → блок в формате `EntityCodec`, с версией, вид — по имени), формат сохранения 4. Выгружаются и загружаются вместе с чанком, проверяются при чтении, как чанки | Предмет, брошенный у дома, лежит там и после перезапуска; без своего чанка сущность не живёт |
| Здоровье | У игрока 20 единиц, на экране — полоса над хотбаром (выбор пользователя: полоса, а не сердца). Урон от падения: высота падения сверх 3 блоков, по единице за блок; считает сервер по принятым позициям (самая высокая точка с прошлого касания земли). Восстановление — единица за 4 с, пока голода нет. В творческом урона нет | Минимальная, но настоящая угроза; голод и бой — следующие этапы |
| Смерть | Выбор пользователя: инвентарь (и курсор) выпадает предметами на месте смерти, они живут обычные 5 минут; экран «Вы погибли» с кнопкой возрождения; игрок появляется в точке появления мира с полным здоровьем | Смерть что-то значит, а выпавшие предметы сразу для этого пригодились |
| Моды | `IWorld.SpawnItem(позиция, стопка)`, `IPlayer.Health` и `IPlayer.Damage(количество, причина)`; события `ItemPickedUp`, `PlayerDamaged`, `PlayerDied`. Свои виды сущностей и компоненты модов — когда появятся мобы | Всё новое доступно модам тем же путём, что ваниль; API компонентов проектировать без второго вида сущностей рано |

### Открытые вопросы этапа 7

- Интерполяция сущностей — между двумя последними тиками клиента, а сервер тикает в своём потоке без синхронизации с клиентом. Если в один тик клиента пришли сообщения двух тиков сервера (или ни одного), движение на мгновение дёргается. Для лежащих и медленно падающих предметов не заметно; для мобов (позже) — возможно, понадобится буфер с задержкой на тик.
- ~~Сущности в чанках, которые сервер выгрузил из памяти, остаются в мире сущностей.~~ Решено на шаге 7.4: выгружаются и сохраняются вместе с чанком.
- Предметы рисуются без отсечения по пирамиде видимости: все известные клиенту, одним вызовом. Число — в строке `[Client] Чанков …` (`сущностей N`); замер на 1000 предметов — шаг 7.6.
- Предмет, брошенный в упор в стену, вылетает из центра тела игрока и ложится у его ног — так задумано (не застревает в стене).
- Рассылка сущностей (`EntitySync`) обходит все предметы для каждого игрока: 0,38 мс тика на 1000 лежащих предметов и одного игрока. Растёт с числом игроков — до мультиплеера пусть так; потом — индекс сущностей по чанкам.
- Замеры этапа 7 сняты на другой машине (Windows, UHD 730), чем замеры этапа 6 (Linux, Iris Xe): сравнение с ними — только по порядку величины.
- Урон виден только по полосе: ни вспышки, ни звука (частиц и звуков в этапе 7 нет).

### Не входит в этап 7

### Критерии завершения этапа

- Добыча падает предметом и подбирается; предметы можно выбросить, они сливаются, исчезают через 5 минут и переживают перезапуск; ничего не теряется и не множится.
- Падение ранит, смерть роняет вещи на месте и возвращает в точку появления; в творческом урона нет.
- Сущности живут на сервере в своём ECS, клиент их только показывает; моды создают предметы, наносят урон и подписываются на новые события.
- Существующие миры открываются; сборка без ошибок и предупреждений, все тесты зелёные; тысяча предметов не роняет кадр и тик ниже замеров этапа 6.

## 16. План этапа 8: свет и время суток

**Цель:** у мира появляется свет. Солнце освещает поверхность, под навесами и в пещерах темно, свет плавный, углы и стыки блоков затенены. Сутки сменяются: 30 минут дня, 10 минут ночи, небо меняет цвет, по нему идут солнце и луна. Ночью и под землёй нужен факел — его делают из древесного угля, он ставится на пол и освещает округу. Свет считает сервер: потом от него будут зависеть появление мобов и рост растений.

### Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Уровни света | Два канала по 4 бита, 0–15, в одном байте на блок: **небесный** (солнце сверху) и **блочный** (факелы). Свет гаснет на 1 за блок, непрозрачный блок его не пропускает, небесный свет 15 идёт вниз без потерь. Время суток в данные света не входит: шейдер умножает небесный канал на яркость неба | Стандартная схема (Minecraft, Minetest). Смена дня и ночи не перестраивает ни свет, ни меши — только одно число в шейдере |
| Где считается | На сервере, общим кодом `Shared.Lighting` (`LightEngine`): заливка очередями (добавление и снятие света при смене блока, как в Minecraft), свет — массив рядом с блоками чанка. В сохранение свет не пишется — считается заново при загрузке | Сервер авторитетен, и свет понадобится его же логике (мобы, рост). Не хранить — меньше формат и нет рассинхрона «блоки новые, свет старый»; цена — замером |
| Солнце над незагруженным | Чанки кубические, над верхним загруженным может быть что угодно. Правило: в незагруженный чанк над столбцом солнце проходит, если его низ выше **естественной высоты** столбца — рельеф и деревья по генератору (`TerrainGenerator`, без генерации чанка). Свет внутри загруженных чанков считается честно | Без столбцов на всю высоту другого источника правды нет. Цена: крыша, построенная выше загруженной полосы (больше 128 блоков над игроком), не даёт тени, а шахта с поверхности глубже 128 блоков не пропускает солнце до дна — в открытые вопросы |
| Передача клиенту | `ChunkData` несёт и свет (свой кодек, палитра + Deflate, как у блоков). Изменение света от поставленного блока или пришедшего соседа — `ChunkLightChanged` (весь свет чанка заново; не `ChunkLight` — имя занято классом света) для каждого затронутого чанка, в том же тике, что `BlockChanged`. Клиент сам свет не считает | Один путь для всех причин изменения. Свет сжимается хорошо (в основном 15 и 0); если окажется дорого — разница вместо целого (замер шага 8.2) |
| Вид | Выбор пользователя: **плавный свет и затенение углов** (smooth lighting + ambient occlusion): свет в каждой вершине грани — среднее четырёх блоков у этого угла, затенение — по трём соседям угла; квадрат разбивается по той диагонали, где перепад меньше (иначе полосы). Постоянная яркость граней (`BlockFace.Brightness`) остаётся множителем | Объём читается намного лучше, а меши и так строятся в фоне. Для углов снимку (`ChunkSnapshot`) нужны рёбра и углы рамки — теперь они заполняются (блоки и свет), отсутствующий диагональный сосед — воздух с полным небом |
| Тёмное | Итоговая яркость — `max(блочный, небесный × яркость неба)` по кривой (уровень 0 — не чёрный, чуть видно), блочный свет чуть тёплый. Предметы на земле берут свет своего блока | Совсем чёрные пещеры неиграбельны; тёплый оттенок отличает факел от луны |
| Сутки | Выбор пользователя: **30 минут день, 10 минут ночь** (40 минут, 48 000 тиков). Переходы — по минуте на рассвет и закат на границах. Время — счётчик тиков мира на сервере, хранится в `meta` (ключ `time`; формат сохранения не меняется: нет ключа — утро), клиенту — в `JoinAccepted` и раз в 10 с `TimeSync`, между ними клиент считает сам. Новый мир начинается утром. Яркость неба ночью — 4/15 | Тики сервера — единственные часы мира. Ключ в `meta` не ломает старые миры и не требует обновления схемы |
| Небо | Цвет фона (`ClearColor`) и туман по краю прорисовки меняются по времени; солнце и луна — квадраты-картинки на небесной сфере, по кругу с востока на запад | Время видно без интерфейса. Туман прячет край мира и заодно покажет ночь вдали |
| Факел | Выбор пользователя: **факел из древесного угля**. `base:charcoal` — бревно в печи; уголь + палка → 4 факела у верстака. Факел — первый некубический блок: поле `model` в JSON блока (`cube` по умолчанию, `torch` — столбик 2 × 10 × 2 пикселя в центре), не твёрдый, не непрозрачный, твёрдость 0, свет 14. Ставится только на верх твёрдого блока; убрали опору — факел ломается с добычей. Задание «Да будет свет» после печи | Встраивается в существующую петлю без новой руды. Модель по имени — задел под растения и другие формы; правило опоры — первое «обновление соседа» |
| Свет в контенте | Поле `light` (0–15) у блока; ванильный — только факел. Свет блока — свойство `BlockDefinition` (нужно серверу), а не только клиенту | Моды делают светящиеся блоки данными |
| Проверка | Клавиша T — +1 час (1/24 суток, временно, как G: до команд), время суток — в заголовке окна | Ждать ночь 30 минут на каждой проверке нельзя |
| Моды | `IWorld.GetLight(позиция)` (небесный и блочный), `IWorld.Time` (тик мира, доля суток, день/ночь); поле `light` и `model` в руководстве. Пример мода: аметистовая руда светится | Всё новое доступно модам тем же путём, что ваниль |

### Открытые вопросы этапа 8

- Солнце над незагруженным — по естественному рельефу: крыша выше загруженной полосы (больше 128 блоков над игроком) тени не даёт, а шахта с поверхности глубже 128 блоков не пропускает солнце до дна. Если станет заметно — хранить высоты столбцов с правками игроков.
- ~~Первый чанк каждого столбца на сервере считает естественную высоту 1024 столбцов шумом (`NaturalTops`) в потоке сервера.~~ Решено на шаге 8.2: её считают потоки генерации (`NaturalSky.Prepare`), замер — 131 мс за вход ушли из тика.
- ~~`ServerHostTests.LongTick…` (открытый вопрос этапа 6) падает примерно в одном полном прогоне из трёх.~~ Решено на шаге 8.2: тест считал тики часами потока теста, а под нагрузкой хост опаздывает меньше `MaxLagSeconds` (это догоняется позже) или ещё раз больше (это тоже копится в `SkippedSeconds`). Теперь начало каждого тика и пропущенное записывает сам тик, а проверка — граница из устройства хоста: тик никогда не начинается раньше расписания (k-й после долгого — не раньше «конец долгого + (k − 1) × 50 мс»), пропущенное читается в первом тике после долгого. Так же переделан `TickRate_MatchesTicksPerSecond` (под нагрузкой на все ядра упал один раз из четырёх): нижняя граница — расписание, слишком редкие тики ловит медианное опоздание. Мутации (10 и 40 Гц, догон вместо пропуска, неверный учёт пропущенного) пойманы; под нагрузкой на все 12 ядер — 4 полных прогона из 4 зелёные.
- Тик в полёте стал тяжелее этапа 7 (Release: средний 2–3,6 мс против 0,5–0,7, максимум 17–24 против 5–17; Debug: 8–18 против 1,2–1,8, максимум до 59 мс). Основное — свет пришедших чанков (бюджет 15 мс за тик в Debug занят почти всегда) и выгрузка раз в секунду (до 25–40 мс за проход). Если станет мешать: меньший бюджет прихода, выгрузка тоже по бюджету тика, ускорение заливки (замер шага 8.6 — полёт).
- Вершина меша выросла до 36 байт (свет — два float). Сжатие вершины (позиции и UV — маленькие целые, свет — 4 бита, затенение — 2 бита) — отдельный шаг оптимизации, если загрузка мешей станет мешать.
- `ChunkLightChanged` шлёт весь свет чанка: в полёте ~150 сообщений и ~270 КБ за 40 с, при входе — десятки. Пока дёшево; разница вместо целого — если понадобится.

### Не входит в этап 8

Цветной свет (RGB); тени от солнца в реальном времени и угол солнца в расчёте света; облака и погода; полупрозрачные блоки (листва с альфой, вода, стекло); факел на стене и другие крепления; блоки, светящиеся по состоянию (печь при плавке); кровать и пропуск ночи; мобы, которые появляются в темноте (свет для этого готовится, сами мобы — следующие этапы); настройки графики (выключить плавный свет); хранение света в сохранении (только если расчёт при загрузке окажется дорогим — по замерам).

### Критерии завершения этапа

- Поверхность освещена солнцем, под навесами и в пещерах темно, свет плавный, углы затенены, на границах чанков нет швов.
- Сутки сменяются (30 минут день, 10 ночь), небо, солнце и луна следуют времени; время переживает перезапуск.
- Факел делается из древесного угля, ставится, светит и ломается без опоры; свет после любых правок равен свету «посчитанному с нуля».
- Свет и время доступны модам; существующие миры открываются.
- Сборка без ошибок и предупреждений, все тесты зелёные; вход и полёт не медленнее этапа 7 сверх разброса (по замерам).
